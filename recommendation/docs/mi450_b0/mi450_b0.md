# Bring-up on MI450 B0, host `heliosr-1b112-a30-4` (gfx1250, single GPU)

**What this is.** The record of getting the MLPerf HSTU/DLRM recommendation
training e2e running on a single MI450 B0 GPU. It is written to be picked up cold
by someone who has not followed the investigation.

**Read it in order.** [§1](#1-the-machine-and-the-software-stack) is the machine
and the flags you must set. [§2](#2-the-open-blocker-train_lossnan-at-step-1370)
is the one thing still broken. [§3](#3-reproducing-the-nan) is how to reproduce
it in about two minutes. Everything after that is settled: §4 is the full list of
changes the e2e needs, §§5–7 are defects already fixed or worked around, kept
because two of them are not upstream and one of them can come back.

| **Leading suspect** | **Kernel overlap on gfx1250** (a0 defect `[7]`), not any one kernel's addressing. `_hstu_attn_fwd` is named in the fault but its addressing audits clean, so it is probably the victim → [§3.3](#33-suspicious-root-causes-ranked-by-confidence) |
| **Next step** | Attribute the fault to a PC with `HSA_COREDUMP_PATTERN` or kernel-disable bisection → [§3.4](#34-next-steps) |
| **Before you run anything** | Three flags are mandatory and one of them wedges the node if you get it wrong → [§1.3](#13-mandatory-flags-and-boot-procedure) |
| **Not the blocker** | Memory faults. Every one of them now has a fix or a workaround — §§5–7 |

**The single most important idea in this document.** A wild GPU store behaves
completely differently depending on how much memory the process has mapped. In a
small probe it lands in unmapped memory and **faults loudly**. In the ~150 GB
training process it lands in a live allocation and **silently poisons it**. That
is why the e2e shows a `nan` with a clean `dmesg` while a two-minute reproducer
of the same defect shows a hard memory fault. Do not treat "no fault" as "no
memory bug", and do not treat the small repro's fault as a different problem from
the e2e's `nan`.

> **b0 and a0 cannot be told apart from software.** They are
> indistinguishable through PCI and VBIOS. Both read device rev **`0x00`** and

The failure is not specific to a container image or to a Docker version. Two

Three things to read off that table:

- **Docker itself differs from a0** (`29.7.2` here vs `29.6.1` there) and is
  **not the variable**: a container runtime does not sit in the path between a
  kernel's `global_load` and the `UTCL2` translation that faults. It is recorded
  only so the two hosts' stacks can be diffed completely.
- **The newer `20260910` image does not help.** It was pulled specifically to
  test whether a userspace refresh fixes this. It does not.
- **The `20260910` image carries stock Triton `3.6.0`, not the `7ff97e3109`
  build**, so it is *not* a like-for-like e2e comparison against a0's recipe —
  but that does not weaken the result, because the corruption reproduces there
  through the **ATen arms, which need no Triton at all**
  ([§7](#7-if-gather-corruption-returns-the-ac-power-cycle)).

One caveat stated for completeness: the `:gfx1250` image here is a **local build**
of [`Dockerfile.amdprimus0815`](../../Dockerfile.amdprimus0815), not a pulled
digest, so it is not provably bit-identical to the image a0 ran. Its torch,
Triton, ROCm and Python versions all match a0's recorded pins.

### 1.3 Mandatory flags and boot procedure

**Three settings are not optional.** Full rationale and the rest of the change
list are in [§4](#4-changes-required-to-run-the-e2e-on-b0); this is the minimum
to not break the host.

| | Why |
|---|---|
| **`AMDGCN_USE_BUFFER_OPS=0`** | `1` **wedges the whole node** and costs a reboot. Inherited from a0 `[1]`. The runner scripts already default it |
| **`PYTORCH_CUDA_ALLOC_CONF=`** (empty) | `expandable_segments:True` caps the torch allocator at **19 GiB of a 432 GiB card** → [§6](#6-worked-around-expandable_segmentstrue-caps-vram-at-19-gib) |
| **`amd-smi`, never `rocm-smi`** | `rocm-smi` is broken here — `NameError: SMI_HASH` |

**Loading the driver.** The kernel cmdline blacklists `amdgpu`, so nothing loads
it automatically. After every boot or power cycle, by hand:

```bash
sudo modprobe amdgpu gpu_recovery=0      # verify: cat /sys/module/amdgpu/initstate -> live
```

> **Never run `/opt/amd-apps/fw-bringup/scripts/setup/post-reboot-gpu.sh` on this
> host.** Its Step 1 (DF Venice toollib) crashes the *subsequent* driver load — a
> NULL deref in `gfx_v12_1_xcc_cp_resume` inside `amdgpu_pci_probe`, reproduced 3×
> on 2026-09-16 — and all its SMN writes read back zero, i.e. it is not
> functioning here. The host is **not in `fw-bringup/config/machines.yaml` at
> all**; the procedure was never meant for it.
>
> If a load does oops, the module sticks in `MODULE_STATE_COMING` with **no
> in-band recovery** (`CONFIG_MODULE_FORCE_UNLOAD` is unset, there is no
> `bind`/`unbind`), and only a reboot clears it. `modprobe -r amdgpu` on a live
> driver after the toollib has altered IP state wedges the board **past warm
> reset**.

**Running the e2e.** Container `triton-7ff97e-test`:

```bash
SMOKE=1 SMOKE_BATCHES=600 scripts/run_prod_convergence_1gpu.sh <logfile>
```

Recipe details in [`mi450_a0.md` §2.2](../mi450_a0/mi450_a0.md).

## 2. The open blocker: `train_loss=nan` at step 1370

**The symptom.** With every change in [§4](#4-changes-required-to-run-the-e2e-on-b0)
applied, the batch-1024 e2e trains normally to **step 1370 of 3000** and then
reports `train_loss=nan`, and stays `nan` for the rest of the run. There is no
memory fault, no Python traceback and nothing in `dmesg`.

**It is a second, distinct defect from the int32 wrap.** `[b3]`
([§5](#5-fixed-an-int32-address-wrap-in-triton_layer_normpy-b3)) was a real bug
and its fix is load-bearing — but it **moved the failure rather than removing
it**. Run `b1024_a30_i64fix_0916_0455` (SEED=1, batch 1024,
`expandable_segments:True` left on):

| | pre-fix (int32) | post-fix (int64) |
|---|---|---|
| first `train_loss=nan` | step 300 | **step 1370** |
| persists to end | yes | yes (1380, 1390, 1400 …) |
| fault / traceback / `dmesg` | none | none |

Throughput was flat at 555.0 samples/s across the transition, so nothing stalled
or fell back — the arithmetic simply went non-finite.

**What has been ruled out.** A static audit of every
`<var>[:, None] * stride_*` in `ops/triton/` found 26 sites outside the two
already-widened files. The two highest-risk were read directly —
`triton_jagged.py:329` (`_jagged_dense_bmm`) and `triton_position.py:112` — and
**both use the correct idiom**: the base pointer is advanced by an `int64`
offset (`Jagged += (seq_start + start_m) * stride_jm`, `SeqEmb +=
seq_start.to(tl.int64) * stride_sn`) and the surviving tile offsets are bounded
by `BLOCK_M` or by `seq_len ≤ MAX_SEQ_LEN = 4096`. So they cannot reach 2³¹.
**A third wrap of [b3]'s form is not obviously present.** The remaining 24 sites
are unread.

**Readings, none yet distinguished:**

1. **A fourth int32 site of a *different* shape** — not row-major `rows * stride`,
   so the audit's pattern would miss it. A smaller stride wraps at a *higher*
   row, which fits an onset that moved later rather than disappearing.
2. **The wild-store / allocator-accident class**, still live. a0 records the
   onset *wandering* under an identical seed (step 91 vs ~190), so 300 → 1370
   may be partly allocator layout rather than the fix.
3. **A non-addressing defect** — numerics, atomics, or a miscompile.

**The one cheap experiment that separates (1)/(3) from (2):** re-run with the
same `SEED=1` and see whether the onset **moves**. A fixed 1370 means
deterministic behaviour with a specific cause to find; a wandering onset means
the wild-store class is still live and the residual is an *address* bug.
~45 min to reach the onset. Nothing else should be changed in that run.

Doing [b4] next is now more attractive than it was: the 19 GiB arena
([§6](#6-worked-around-expandable_segmentstrue-caps-vram-at-19-gib)) shapes
*where* a wild store lands, so unsetting it is both a fix on its own merits and
a perturbation of reading (2).

## 3. Reproducing the `nan`

**The blocker, in three lines.** The batch-1024 e2e trains normally to **step 1370
of 3000** and then reports `train_loss=nan` for the rest of the run
([§2](#2-the-open-blocker-train_lossnan-at-step-1370)). There is no fault, no
traceback, nothing in `dmesg`, and throughput is flat across the transition. All of
that says *silent memory corruption*, not a numerical blow-up.

**Pick your reproducer.** Both drive **one HSTU layer** at production shapes — no
dataset, no torchrec, no embedding tables, no distributed init. Define this once and
the `Command` column is copy-pasteable as written:

```bash
gr() {                          # $EXTRA prepends env vars, e.g. EXTRA=AMD_SERIALIZE_KERNEL=3
  docker exec -e AMDGCN_USE_BUFFER_OPS=0 -e PYTORCH_CUDA_ALLOC_CONF= triton-7ff97e-test \
    bash -lc "cd /workspace/recommendation; $EXTRA python scripts/$*"
}
```

| Reproducer | Command | Time to fault | Regime | Use it for | Do **not** use it for |
|---|---|---|---|---|---|
| **`repro_gfx1250_nondeterminism.py`** — feeds byte-identical input repeatedly and checks the answer never changes | `gr repro_gfx1250_nondeterminism.py --rows 2800000 --path triton --repeats 400 --backward` | median **~5 min**; **budget ~20 min**. 509 s buys 400 fwd + 400 bwd repeats → ~0.75 s/repeat, at ~1 fault/300 | **Single stream, single process — the same regime as the e2e** | **Every claim in [§3.1](#31-what-the-reproducer-shows)–[§3.2](#32-what-we-conclude).** The only arm whose result is evidence about the 1370 `nan` | A quick health check. It is Poisson — a clean 400 has a **~1-in-4 chance of being luck**, and a pass proves nothing |
| **`repro_gfx1250_fast_fault.py`** — two independent fwd+bwd loops, one per stream, sharing nothing but the GPU | `gr repro_gfx1250_fast_fault.py --rows 400000 --streams 2` | **24–31 s, 3/3 runs** (~500× faster) | **Two streams.** The e2e is single-stream (`use_pipeline=False`) | Handing a vendor a 25-second repro. Produces the **same wild-store signature**: `GC_UTCL2` / `TCP (0x8)` / `RW: 0x1` | Evidence about the 1370 `nan`. Same signature, **unproven same defect** — and neither available control can settle it: `AMD_SERIALIZE_KERNEL=3` and a per-thread `torch.cuda.synchronize()` both still fault, because two threads overlap across separate HSA queues |

**Three things you must get right — for either script:**

- `AMDGCN_USE_BUFFER_OPS=0` is **mandatory** — `1` wedges the whole node.
- `PYTORCH_CUDA_ALLOC_CONF` must be **empty** ([§6](#6-worked-around-expandable_segmentstrue-caps-vram-at-19-gib)).
- **Run on an otherwise idle GPU.** A concurrent GPU job corrupts the result on its
  own ([§3.6](#36-the-contention-bug-found-alongside--real-but-not-the-nan)).
  Several earlier measurements in this investigation were taken alongside a live
  training process and are worth nothing.

**Failure** is a hard `HSA_STATUS_ERROR_MEMORY_APERTURE_VIOLATION`, naming
`kernel: _hstu_attn_fwd` in the single-stream arm. **Success** is `RESULT: PASS`,
one distinct output hash, `dx` bit-exact — which, per the table, means little on its own.

**Tried and rejected as ways to shorten the single-stream arm** — recorded so
nobody repeats them (all 2026-09-16, idle GPU, tight never-syncing loop):

| Attempt | Command | Result | What it rules out |
|---|---|---|---|
| Tight loop, small N | `gr repro_gfx1250_fast_fault.py --rows 400000 --streams 1` | clean, **4986 iters / 319 s** | A tight never-synchronizing loop is **not sufficient on its own**, and shrinking N to go faster does not work |
| Dead address-space pressure | `gr repro_gfx1250_fast_fault.py --rows 400000 --streams 1 --ballast 8` | clean, **4039 iters / 259 s** | **The defect is not footprint-sensitive.** 8 GiB allocated and never touched changes nothing — which argues against a plain int32 offset wrap of the `[b3]` shape |
| Tight loop, full N | `gr repro_gfx1250_fast_fault.py --rows 2800000 --streams 1` | clean, 342 iters / 363 s | **Nothing.** 342 iterations is about one fault interval, so this arm proves nothing in either direction — do not cite it as a pass |
| Force silent poisoning to fault | `EXTRA=PYTORCH_NO_CUDA_MEMORY_CACHING=1 gr ...` | **not run** | — |

**Caveat on minimality:** it is standalone but **not torch-only** — it imports
`generative_recommenders`, so a vendor needs the repo checked out. Reducing it
further requires knowing which kernel is actually at fault, which is
[§3.4](#34-next-steps)'s first item.

### 3.1 What the reproducer shows

Every arm below: idle GPU, single process, single stream, seed 1, N = 2,800,000
(`max_seq_len` 4096) unless the row says otherwise. Measured 2026-09-16.

**The commands are exact.** Define this once, then the `Command` column is
copy-pasteable as written:

```bash
repro() { gr repro_gfx1250_nondeterminism.py --rows 2800000 --path triton --seed 1 "$@"; }
```

| # | Arm | What it changes vs. the plain run | Repeats | Command | Result | What it establishes |
|---|---|---|---|---|---|---|
| 1 | Forward only | No backward pass at all | 500, then 300, then **1500** | `repro --repeats 500`, then `--repeats 300`, then `--repeats 1500` | **PASS** — one bit-identical output every time | **The forward path is clean** over 2,300 repeats. Whatever fails needs the backward pass present |
| 2 | Forward only, N sweep | N = 1.4M / 2.1M / 2.8M | 3 each | `repro --rows 1400000 --repeats 3`, then `--rows 2100000`, then `--rows 2800000` (the trailing `--rows` overrides the one in the prefix) | PASS, all | **Weak evidence only** — 3 repeats is ~100× below the ~300 needed to see the fault, so this arm cannot clear any N |
| 3 | Forward + backward | — (this *is* the plain run) | 3 | `repro --repeats 3 --backward` | PASS | **Short runs look healthy.** This is why the e2e reached step 1370 |
| 4 | Forward + backward | — | 300 | `repro --repeats 300 --backward` | **FAULT** — `HSA_STATUS_ERROR_MEMORY_APERTURE_VIOLATION` | The defect is real and reachable in ~5 min (300 backward repeats at ~0.75 s each, plus startup) |
| 5 | Forward + backward | — | 400 | `repro --repeats 400 --backward` | **FAULT** — `kernel: _hstu_attn_fwd` | **Names the kernel** — but see §3.2 conclusion 7, it is probably the victim |
| 6 | `AMD_SERIALIZE_KERNEL=3` | Serializes **every** kernel, device-wide | 400 | `EXTRA=AMD_SERIALIZE_KERNEL=3 repro --repeats 400 --backward` | **PASS** | **Kernel overlap is required.** But too blunt to attribute: it changes the thing under test |
| 7 | **`--sync-between`** | One `torch.cuda.synchronize()` between fwd and bwd **only** — nothing inside either is serialized | 400 | `repro --repeats 400 --backward --sync-between` | **PASS** — `dx` bit-exact, 1 distinct hash | Narrows it to **forward/backward overlap** specifically. **But at ~1 fault per 300 repeats, a clean 400 is ~1-in-4 luck — evidence, not proof** |
| 8 | **`--sync-between`** | same as 7 | **1500** | `repro --repeats 1500 --backward --sync-between` | **PASS** — `dx` bit-exact every repeat, 1 distinct hash, 0 faults | **Decisive.** 1500 clean is 5× the mean fault interval; the plain arm faults twice in 700. **Forward/backward overlap is required**, and one `synchronize()` in the right place suppresses the defect entirely |

**Rate:** roughly **1 fault per ~300 backward repeats**. Rows 3 and 2 are short
enough that a PASS there means nothing; only rows 6–8 are long enough to carry a
negative result, and only row 8 is long enough to carry it confidently.

**Reading the fault signature.** Rows 4 and 5 produce this in `dmesg`:

```
[gfxhub0] no-retry page fault (src_id:0 ring:40 vmid:3 pasid:61)
  in page starting at address 0x0000705707600000 from IH client 27 (GC_UTCL2)
  Faulty UTCL2 client ID: TCP (0x8)
  PERMISSION_FAULTS: 0x5      RW: 0x1      MAPPING_ERROR: 0x0   WALKER_ERROR: 0x0
```

| Field | Value | What it means |
|---|---|---|
| IH client | `27 (GC_UTCL2)` | The graphics L2 translation unit raised it — a shader memory access, not DMA or display |
| UTCL2 client ID | `TCP (0x8)` | The vector/texture data cache — i.e. a **vector memory instruction in a kernel** |
| **`RW`** | **`0x1`** | **A write.** This is the single most diagnostic field: the kernel stored somewhere it should not have |
| `MAPPING_ERROR` / `WALKER_ERROR` | `0x0` / `0x0` | The address **translated fine**; the page simply is not writable by this process. So it is a plausible-looking but wrong address, not garbage |
| `PERMISSION_FAULTS` | `0x5` | Write to a page without write permission |

**`GC_UTCL2` / `TCP (0x8)` / `RW: 0x1` is the same triple** as the original step-212
e2e fault and as the `_weighted_layer_norm_fwd` int32 wrap in
[§5](#5-fixed-an-int32-address-wrap-in-triton_layer_normpy-b3) — both confirmed wild
stores. That is the basis for calling this one a wild store too.

### 3.2 What we conclude

Ranked by confidence, highest first. "From" cites the arm numbers in
[§3.1](#31-what-the-reproducer-shows); "#" is a stable id — other sections cite
these numbers, so they do not renumber when the ranking changes.

| Confidence | # | Conclusion | Component implicated / cleared | From | Why we are this confident | Why it matters |
|---|---|---|---|---|---|---|
| **High** | 1 | **It is a memory-safety defect — a wild store**, not a numerical blow-up | **Triton codegen / LLVM — or gfx1250 silicon.** Excludes the model math, PyTorch eager, and TorchRec: none of those can emit a raw store to a wrong address | 4, 5 | The hardware says so directly: `RW: 0x1` in the fault record is a *write*, and `MAPPING_ERROR`/`WALKER_ERROR` are both `0x0`, so the address translated fine — a plausible wrong address, not garbage. Same signature as two *confirmed* wild stores on this host (`[b3]`, §3.6) | Sets the whole search: look for an address computation, not for overflow/underflow in the math |
| **High** | 2 | **The backward pass is required** | **The Triton backward kernels in `ops/triton/`.** Same tree as `[b3]`. Excludes the forward kernels and everything above Triton | 1 vs 4 | Forward-only is clean over 2,300 cumulative repeats (arms 1–3) at the same shapes where fwd+bwd faults at 300–400 (arms 4–5). That is ~8× the mean fault interval with zero events | Halves the search space — forward-only kernels can be deprioritised |
| **High** | 3 | **Forward/backward overlap is required** | **gfx1250 silicon + the ROCm/HSA dispatch path**, not Triton source. Triton decides *what* each kernel addresses; the runtime and hardware decide *what runs alongside it* | 6, 7, 8 | **Settled by arm 8.** Arm 6 (`AMD_SERIALIZE_KERNEL=3`) suppressed it but was too blunt to attribute. Arm 7 (`--sync-between`, one `synchronize()` between fwd and bwd) passed 400, which had a ~1-in-4 chance of being luck — so arm 8 ran it to **1500 clean**, 5× the mean fault interval, against a plain arm that faults twice in 700. ### 3.6 The contention bug found alongside — real, but not the `nan`

A second, genuine defect surfaced while chasing this, and it is **not** the `nan`:
**concurrent high-VGPR GPU work corrupts or faults other GPU work on this host.**

| Aggressor | GFX | Victim: distinct outputs / 20 identical calls | Worst error |
|---|---|---|---|
| none (idle) | 0 % | **1** — 120/120 clean, 3 procs, both paths | — |
| bf16 GEMM + gather, 150 GiB | 100 % | ~1 event in 420 calls | 1.3e-05 |
| **Triton HSTU fwd+bwd, separate process** | 100 % | **7, 9, 7 → ~35 % of calls wrong** | **1.8e-01** |
| **Triton HSTU, same process, 2nd stream** | 100 % | **hard fault** in `_hstu_attn_bwd` | — |
| none again, straight after | 0 % | **1, byte-identical to the idle row** | — |

- **Not "the GPU is busy"** — both aggressors pin GFX at 100 %; only the high-VGPR
  one corrupts, 175x more often. This is a0 defect **[7] high-VGPR + concurrent
  streams**, now with a rate and a reproducer.
- **Not a Triton bug** — under the HSTU aggressor **PyTorch is the worse victim**.
  The victim path is incidental.
- **Not latched** — it clears the moment the aggressor stops, and the correct
  answer is bit-identical before and after. **Do not AC power-cycle for this one**;
  that was [§7](#7-if-gather-corruption-returns-the-ac-power-cycle), a
  different bug.
- **Why it is not the 1370 `nan`:** the e2e is single-stream.
  `train_loop()` takes `use_pipeline: bool = False`
  ([`train/utils.py:1720`](../../generative_recommenders/dlrm_v4/train/utils.py)),
  `train_ranker.py:387` does not pass it, and nothing else sets it — so TorchRec's
  overlap pipeline is off, and on 1 GPU there is no a2a either.
  **Caveat, added after the `_hstu_attn_fwd` audit:** this argument excludes
  *concurrent streams*, and that is all it excludes. `AMD_SERIALIZE_KERNEL=3`
  suppresses the §3.1 fault in a reproducer that is itself single-stream, so a
  **same-stream** variant of this defect exists and *is* available in the e2e.
  See the end of [§3.1](#31-what-the-reproducer-shows).

**Consequence for this whole investigation:** any number taken on this host while
another GPU job was running is suspect, **including `probe.py` runs used to declare
the host healthy**. A clean `probe.py` is necessary, not sufficient. Re-take
anything that matters on an idle GPU.

### 5.2 What it is: the same class as [3], in a different file

in **int32**. The pattern, verbatim from `_weighted_rms_norm_fwd`:

```python

    X + rows[:, None] * stride_x + cols[None, :],   # address from the WRAPPED product
    mask=mask_2d, other=0.0,
)
```

This is [3]'s exact signature: **the bounds check and the address are computed
from different values.** `rows < N` passes, while `rows * stride_x` has already
wrapped negative, so the masked access is *enabled* and lands ~8 GiB below the
tensor.

**Thirteen un-widened sites, while the same file widens elsewhere** — [3]'s
"neighbours widen, this one doesn't" tell:

| Kernel | Un-widened `rows[:, None] * stride_*` | Note |
|---|---|---|
| `_layer_norm_fwd` (:109) | `:134`, `:164` | |
| **`_weighted_layer_norm_fwd`** (:175) | **`:208`, `:242`** | **on the HSTU path** (`ops/hstu_compute.py:106`); **reproduced below** |
| `_weighted_layer_norm_bwd_dx` (:297) | `:342`, `:347`, `:385`, `:398` | |
| **`_weighted_rms_norm_fwd`** (:790) | **`:817`, `:839`** | a0 flagged this one **by name** as unprotected |
| `_weighted_rms_norm_bwd_dx` (:846) | `:954`, `:959`, `:988` | |

Already widened in the same file: `row.to(tl.int64)` at `:265`–`:267`, `:865`–`:867`,
and `pid.to(tl.int64)` at `:410`–`:411`.

### 5.3 The reproducer — confirmed, to the row and to the byte

[`scripts/repro_gfx1250_layernorm_i32.py`](../../scripts/repro_gfx1250_layernorm_i32.py).
`torch` plus the repo's public `layer_norm` / `rms_norm` wrappers — no dataset, no
fbgemm, no TorchRec, no training loop.

At `D = 512` the wrap row is `2**31 / 512 = 4,194,304`:

```
N=1,000,000   bad_rows=0  canary_bad=0   PASS
N=2,740,000   bad_rows=0  canary_bad=0   PASS     <- a0's estimate of production jagged N
N=4,194,303   bad_rows=0  canary_bad=0   PASS
N=4,194,304   bad_rows=0  canary_bad=0   PASS     <- max offset 2,147,483,136, just under 2**31-1
N=4,194,305   MEMORY FAULT in _weighted_layer_norm_fwd
```

**Predicted to the row**, and the fault address confirms the mechanism to the byte:

| | |
|---|---|
| `y` base | `0x705907a00000` |
| faulting address | `0x705707600000` |
| delta | **8,594,128,896 B = 8.004 GiB** |
| `2**31` elements × 4 B | **8 GiB** |

An int32 offset wrapping negative, exactly. `dmesg`:

### 5.4 What the reproducer does *not* establish

Stated plainly, because it is the one gap between this defect and the NaN:

- **Whether production reaches `N > 4,194,304` was the open question — and the
  e2e A/B in [§5.5](#55-the-fix) now says it does.** An int64 widening is a
  *no-op* unless something exceeds int32, and it changed the outcome at step 300,
  so something did. The reconciliation with a0's `N ≈ 2.74M` is that **jagged `N`
  varies per batch**: sequence lengths differ, so `total_rows` is not fixed, and a
  corpus *average* says nothing about the tail. The wrap fires on whichever batch
  first exceeds 4,194,304 rows.

  This also explains the **wandering onset** (a0 saw step 91 vs ~190 under an
  identical seed) better than the allocator-accident story does: it is which
  *batch* is large enough, not which tensor happens to sit below `Y`.

  Still worth measuring `N` directly — but for its **maximum and distribution**,
  not its mean. `N` is known by step 1, so a ~5-step instrumented run answers it.
- **A tempting coincidence that does *not* hold up:** `1024 × 4096 × 512 = 2**31`
  exactly, i.e. `BATCH_SIZE × MAX_SEQ_LEN` *is* the wrap row. But there is **no
  `jagged_to_padded` conversion on the HSTU path** — `layer_norm` receives the
  jagged `[total_rows, D]` tensor, with 1.53× margin. This was the leading
  candidate and the arithmetic does not support it.
- **The reproducer faults; production NaNs.** Not a contradiction — it faults only
  because in a small probe the memory 8 GiB below `y` is unmapped. In the
  training process, holding ~150 GB, that address lands in **live allocations**,
  so the wild store poisons rather than faults. That silent-poisoning asymmetry
  is [3]'s recorded signature.
- The 6 GiB canary was too small to catch an 8 GiB-below access. Catching the
  silent case needs a canary **> 8 GiB allocated *below* `y`** — and this
  allocator hands out *descending* addresses, so the canary must be allocated
  *after* `y`, which means driving the Triton kernel directly instead of through
  the wrapper.
- **`rms_norm` and `N = WRAP + 100_000` were never run** — the script aborted at
  the first fault.

### 5.4b Why a0's [3] fix did not already cover this

a0 fixed this **defect class** and the fix **is** in the repo — commit `1a3dcd6`,
*"Fix int32 row-offset overflow in `_ln_mul_dropout_fwd_rng` (gfx1250 nan)"*. But
`git show --name-only 1a3dcd6` lists exactly one file:
`generative_recommenders/ops/triton/triton_hstu_linear.py`. **It never touched
`triton_layer_norm.py`.**

The commit states its audit was complete — *"The backward kernels were audited …
so the forward was the only defect"* — and that is true **within that file**. The
audit never crossed into `triton_layer_norm.py`, which carries the identical
pattern in five kernels.

**Why a0's run passed anyway: the wrap rows differ by 3×.**

| | kernel | stride | wrap row |
|---|---|---|---|
| a0 fixed (`1a3dcd6`) | `_ln_mul_dropout_fwd_rng` | `3*D` = 1536 | **1,398,102** |
| fixed here ([§5.5](#55-the-fix)) | `_weighted_layer_norm_fwd` | `D` = 512 | **4,194,304** |

At jagged `N ≈ 2.74M`, a0's kernel wrapped on **essentially every batch** — hence
NaN by step ~190, 2/2. `triton_layer_norm.py` needs `N > 4.19M`, so it trips only
on unusually large batches. **a0's 600 clean steps were not evidence that file was
safe; they were the rarer trip not yet happening.** This is a0's own reasoning
from the same commit — *"Batch size enters only by scaling N past the wrap row,
which is why this presents as batch-gated while being a pure row-count bug"* —
simply never applied to the second file.

> **Consequences worth acting on:**
> - The [§5.5](#55-the-fix) fix is **new work, not a re-application**, and
>   belongs upstream. **a0 is exposed to it today** and has only been lucky.
> - a0's `600/600` batch-1024 result does **not** clear `triton_layer_norm.py`,
>   and a0's own ≥3000-step bar was never met for these kernels.
> - a0's doc mentions `_weighted_rms_norm_fwd` repeatedly, but always as a
>   **`clamp_num_stages` coverage gap** (defect [4] — it uses a raw
>   `@triton.autotune`), never as an int32 risk. The two were never connected.

### 5.5 The fix

Widen the row index once per kernel and use it for every load and store — the
same shape as [3]'s fix in `triton_hstu_linear.py:186`:

```diff
     rows = start_row + tl.arange(0, BLOCK_N)
     row_mask = rows < N
+    rows_i64 = rows.to(tl.int64)
     mask_2d = row_mask[:, None] & col_mask[None, :]
     x_block = tl.load(
-        X + rows[:, None] * stride_x + cols[None, :],
+        X + rows_i64[:, None] * stride_x + cols[None, :],
         mask=mask_2d, other=0.0,
     ).to(tl.float32)
```

Apply to all 13 sites in the §5.2 table. Keep `row_mask` on the **narrow**
`rows` — widening the comparison is unnecessary and widening only the address is
the entire point.

Cost is negligible: it is address arithmetic on a `BLOCK_N`-sized vector, once per
tile, not per element.

**APPLIED 2026-09-16** to all 13 sites across all 5 kernels (`rows_i64` is defined
once per kernel, immediately after `row_mask`, and used by every strided load and
store; `row_mask` itself stays on the narrow `rows`).

**Verified against the §5.3 reproducer — the fault is gone:**

| `N` | before | after |
|---|---|---|
| 4,194,303 | PASS | PASS |
| 4,194,304 | PASS | PASS |
| **4,194,305** | **MEMORY FAULT** | **PASS** |
| 4,294,304 | *(never reached)* | PASS |
| **8,388,609** | *(never reached)* | **PASS** — two full wraps |

`bad_rows=0`, `nonfinite=0`, `canary_bad=0` at every size, against a `torch`
reference. **`rms_norm` passes the same sweep** — `_weighted_rms_norm_fwd` is the
kernel a0 flagged by name and it had never been exercised past the wrap before.

**Verified end to end** (`b1024_a30_i64fix_0916_0455`, same `SEED=1`, same
container, `expandable_segments:True` deliberately left in place so the fix is
the only variable):

| Step | pre-fix `b1024_a30_postfix_0916_0419` | post-fix |
|---|---|---|
| 260 | 0.13939 | 0.13939 |
| 270 | 0.13846 | 0.1384**7** |
| 280 | 0.13763 | 0.1376**4** |
| 290 | 0.13945 | 0.13945 |
| **300** | **`nan`** | **0.13873** |
| **310** | **`nan`** | **0.13898** |

Bit-identical trajectory up to the cliff, then the pre-fix run NaNs forever and
the patched run continues in band. That is the signature wanted from an
*addressing* fix: it changed which bytes are touched, not what the math computes.
Throughput is unchanged — 550.7 vs a pre-fix mean of 559.4 samples/s, inside the
536.7–586.4 run-to-run spread.

> **The 1e-5 divergences at steps 270 and 280 are not explained.** The benign
> reading — and the likelier one, since step 290 snaps back to an exact match —
> is atomic accumulation order in the `dw`/`db` reduction surfacing in the last
> printed digit. The uncomfortable reading is early silent poisoning in the
> pre-fix run. **Nothing in this data separates them.**

> **Do NOT reach for `DEBUG_NAN_HOOKS` to chase this.**
> [`mi450_a0.md`](../mi450_a0/mi450_a0.md) item 12 records that the hooks are
> unusable on Triton 3.8.0 — they fault at `gstep=0` — and this is that stack.
> `DEBUG_NAN_HOOKS=2` has itself wedged the GPU.

### 5.6 Bar for calling this fixed

a0's bar is **≥3000 steps**, and it is there for a reason: AMD Triton 3.7.1 once
looked fixed at 250 steps and went NaN at 2200. **600 clean steps does not close
this class of defect**, and neither does clearing step 300.

`b1024_a30_i64fix_0916_0455` was the run against this bar. **VERDICT, 2026-09-16:
it FAILED.** Clean through step 1360, `nan` at **1370**, and `nan` at every logged
step after (1380 … 1450+). Throughput was flat at 555.0 samples/s across the
transition, with no fault, no traceback and a clean `dmesg`.

Passing step 300 was strong evidence for the widening — the unpatched run died
there from a bit-identical trajectory — but it was **one cliff, not the bar**,
and the bar is what caught this. The gap between the two is the whole reason a0
set it at 3000. Full analysis in [§2](#2-the-open-blocker-train_lossnan-at-step-1370).

Two things that remain true whatever that run does:

- The fix is correct on its own terms regardless of the e2e outcome — §5.3's
  reproducer faults without it and passes with it, and that is independent of
  whatever else this host does.
- **The `expandable_segments:True` bug in [§6](#6-worked-around-expandable_segmentstrue-caps-vram-at-19-gib)
  is still present in this run**, deliberately, to keep the fix the only variable.
  It should be removed next, on its own merits.

## 6. Worked around: `expandable_segments:True` caps VRAM at 19 GiB

Unrelated to §§5 and 7, found while building the §5 reproducer, and it affects every
run launched from this repo.

Measured by allocating 1 GiB fp32 tensors in a loop inside `triton-7ff97e-test`
(torch `2.11.0+rocm7.14.0a20260625`, gfx1250):

| `PYTORCH_CUDA_ALLOC_CONF` | Result | Peak reserved |
|---|---|---|
| `expandable_segments:True` | **OOM at 19 GiB** | 19.004 GiB |
| *(unset)* | **392 GiB OK** | **399.0 GiB** |

**That is ~5 % of the card.** It is not contention and not partitioning:
`torch.cuda.mem_get_info` reports free = 431.7 GiB / total = 432.0 GiB in *both*
cases, `amd-smi` shows `USED_VRAM: 167 MB` with "No running processes detected"
and no KFD clients, and 256 CUs are visible (so not an XCP slice).

The flag is set in **five** places, including the one the e2e uses:

| Location | |
|---|---|
| [`scripts/run_prod_convergence_1gpu.sh:93`](../../scripts/run_prod_convergence_1gpu.sh#L93) | **the e2e path** |
| `Dockerfile:90`, `Dockerfile.amdprimus0815:137` | container-wide `ENV` |
| `scripts/run_smoke_shrink_1gpu.sh:43`, `scripts/launch_local.sh:73`, `scripts/launch_slurm.sh:610` | |

The e2e trains anyway because fbgemm TBE allocates the ~150 GB of embedding
tables outside the PyTorch caching allocator. But **every torch tensor in the run
is confined to a ~19 GiB arena** — which is also precisely the kind of dense,
fully-live region an 8 GiB-negative wild store would land in. Consistent with
§5's silent-poisoning mechanism; **not evidence for it.**

**Recommended:** re-run the e2e with `PYTORCH_CUDA_ALLOC_CONF` unset. It is a
one-variable change that both removes a demonstrably broken setting and tests
whether the allocator layout is implicated in the NaN.

## 7. If gather corruption returns: the AC power cycle

**This section replaces a ~400-line investigation that is now closed.** Between
2026-09-12 and 2026-09-16 this host silently returned wrong data from gather
operations. It was **not a software bug**, and the reproducers written to chase
it are no longer useful — they all read clean now. What is worth keeping is the
symptom description and the recovery, because **the defect can come back**.

**What it looked like.** `torch.index_select` returned wrong rows — 82–95 % of
trials bad at `D=16`, 26 % at `D=4` — while **dense GEMM in the same process was
provably clean**. It was not a numerics problem: the values returned were other
rows, verbatim. The e2e died at step 212 with a page fault whose `dmesg`
signature was `GC_UTCL2` / client `TCP (0x8)` / `RW: 0x1`.

**Why it is not software.** It survived **8+ warm reboots**. Four independent
container images corrupted identically, including one carrying a *different LLVM
entirely* (ROCm 7.15 + torch 2.10.0). No image, Triton pin, LLVM or driver
package made any difference.

**What fixed it: a full AC power cycle**, with the software stack completely
untouched — out-of-band via BMC `10.5.217.131` (`ipmitool chassis power cycle`),
or at the rack. Before: 82–95 % bad. After: **0/2000**, **0/1000**, and 0/600 on
all 14 arms of the original reproducer. Remember to reload the driver by hand
afterwards ([§1.3](#13-mandatory-flags-and-boot-procedure)).

> **Do not present the AC cycle as a root-cause fix.** "Latched platform state"
> names the behaviour, not a cause — candidates include UTCL2/TCP translation
> state, a DF/fabric configuration register, an SMU artifact, or a soft error in
> a register outside the warm-reset domain. It is a known-working *recovery for
> an open defect*, and that is the form it should take when handed to the
> driver/hardware team. It is also **n=1 and not cleanly attributable**: two
> cycles happened on 2026-09-16 and the GPU could not be measured between them.

**How to tell whether it is back, and why you should check.** The corruption
rates **grew with uptime** — 14.67 % on 2026-09-12 → 82–95 % by 2026-09-16 —
which suggests accumulation rather than a single upset. So:

```bash
docker exec -e PROBE_ITERS=1000 <container> bash -lc 'cd /tmp && python probe.py'
```

**Run this before trusting any long e2e run, and record host uptime with the
measurement.** A clean `probe.py` is **necessary but not sufficient** — see
[§3.6](#36-the-contention-bug-found-alongside--real-but-not-the-nan), which shows
that a concurrent GPU job on this host can corrupt results on its own. Take the
probe on an **idle** GPU.

**Do not confuse this with the current blocker.** The step-1370 `nan`
([§2](#2-the-open-blocker-train_lossnan-at-step-1370)) appeared *after* the AC
cycle, on a host whose gather path reads 0/2000 clean. **An AC cycle is not a
remedy for it** — §3.6's contention effect, unlike this one, is not latched and
clears by itself when the competing job stops.

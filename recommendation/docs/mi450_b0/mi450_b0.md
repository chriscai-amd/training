**Historical hypothesis, separate from the current capture evidence.** A wild GPU store can behave
differently depending on how much memory the process has mapped. In a small
probe it can land in unmapped memory and **fault loudly**; in the ~150 GB
training process it can hit a live allocation and **silently poison it**.
This offers a mechanism linking the small reproducer's memory fault to the
historical e2e NaN, but that link remains circumstantial ([§3.2](#32-what-we-conclude)).
The September 18 timestamp-13 NaN has not been attributed to that mechanism.
A clean `dmesg` does not rule out a memory bug, and matching symptoms alone
do not establish a shared cause.

### 1.3 Mandatory flags and boot procedure

**Three settings are not optional.** Full rationale and the rest of the change
list are in [§4](#4-changes-required-to-run-the-e2e-on-b0); this is the minimum
to not break the host.

| | Why |
|---|---|
| **`AMDGCN_USE_BUFFER_OPS=0`** | `1` **wedges the whole node** and costs a reboot. Inherited from a0 `[1]`. The runner scripts already default it |
| **`PYTORCH_CUDA_ALLOC_CONF=`** (empty) | `expandable_segments:True` caps the torch allocator at **19 GiB of a 432 GiB card** → [§6](#6-worked-around-expandable_segmentstrue-caps-vram-at-19-gib) |
| **`amd-smi`, never `rocm-smi`** | `rocm-smi` is broken here — `NameError: SMI_HASH` |

**Loading the driver.** The kernel cmdline blacklists `amdgpu`, so nothing loads
it automatically. After every boot or power cycle, by hand:

```bash
sudo modprobe amdgpu gpu_recovery=0      # verify: cat /sys/module/amdgpu/initstate -> live
```

> **Never run `/opt/amd-apps/fw-bringup/scripts/setup/post-reboot-gpu.sh` on this
> host.** Its Step 1 (DF Venice toollib) crashes the *subsequent* driver load — a
> NULL deref in `gfx_v12_1_xcc_cp_resume` inside `amdgpu_pci_probe`, reproduced 3×
> on 2026-09-16 — and all its SMN writes read back zero, i.e. it is not
> functioning here. The host is **not in `fw-bringup/config/machines.yaml` at
> all**; the procedure was never meant for it.
>
> If a load does oops, the module sticks in `MODULE_STATE_COMING` with **no
> in-band recovery** (`CONFIG_MODULE_FORCE_UNLOAD` is unset, there is no
> `bind`/`unbind`), and only a reboot clears it. `modprobe -r amdgpu` on a live

## 2. The open blocker: `train_loss=nan` at step 1370

**The reference symptom (September 16, training window 150).** With the source
fixes in [§4](#4-changes-required-to-run-the-e2e-on-b0) applied and
`expandable_segments:True` retained, the batch-1024 e2e trains normally to
**step 1370 of 3000** and then
reports `train_loss=nan`, and stays `nan` for the rest of the run. There is no
memory fault, no Python traceback and nothing in `dmesg`.

**September 18 reproduces NaN with the requested combination.** After an
initial stall and host reboot, the verified September 10 image plus the
exact requested Triton commit, starting at timestamp zero with allocator
settings cleared, logged finite loss at step 50 and **NaN at steps 60/70/80**.
The first observed NaN was in timestamp window 13. This confirms the symptom
under this configuration; it does not establish that its cause is identical
to the historical window-150 failure or isolate the image's effect.
The reproduction and earlier failed automatic recovery are recorded in
[§1.2](#september-18-requested-combination-starting-at-timestamp-zero).

**It is a second, distinct defect from the int32 wrap.** `[b3]`
([§5](#5-fixed-an-int32-address-wrap-in-triton_layer_normpy-b3)) was a real bug
and its fix is load-bearing — but it **moved the failure rather than removing
it**. Run `b1024_a30_i64fix_0916_0455` (SEED=1, batch 1024,
`expandable_segments:True` left on):

| | pre-fix (int32) | post-fix (int64) |
|---|---|---|
| first `train_loss=nan` | step 300 | **step 1370** |
| persists to end | yes | yes (1380, 1390, 1400 …) |
| fault / traceback / `dmesg` | none | none |

Throughput was flat at 555.0 samples/s across the transition, so nothing stalled
or fell back — the arithmetic simply went non-finite.

**What has been ruled out.** A static audit of every
`<var>[:, None] * stride_*` in `ops/triton/` found 26 sites outside the two
already-widened files. The two highest-risk were read directly —
`triton_jagged.py:329` (`_jagged_dense_bmm`) and `triton_position.py:112` — and
**both use the correct idiom**: the base pointer is advanced by an `int64`
offset (`Jagged += (seq_start + start_m) * stride_jm`, `SeqEmb +=
seq_start.to(tl.int64) * stride_sn`) and the surviving tile offsets are bounded
by `BLOCK_M` or by `seq_len ≤ MAX_SEQ_LEN = 4096`. So they cannot reach 2³¹.
**A third wrap of [b3]'s form is not obviously present.** The remaining 24 sites
are unread.

**Readings, none yet distinguished:**

1. **A fourth int32 site of a *different* shape** — not row-major `rows * stride`,
   so the audit's pattern would miss it. A smaller stride wraps at a *higher*
   row, which fits an onset that moved later rather than disappearing.
2. **The wild-store / allocator-accident class**, still live. a0 records the
   onset *wandering* under an identical seed (step 91 vs ~190), so 300 → 1370
   may be partly allocator layout rather than the fix.
3. **A non-addressing defect** — numerics, atomics, or a miscompile.

**A matched rerun can test whether the onset moves:** retain `SEED=1` and the
same execution settings. A changing failure step would show run-to-run
variation, but would not by itself distinguish address corruption, atomics,
numerical instability or a compiler defect. Even a fixed sampled onset would
need operation-level evidence to identify its cause. The September 18 capped
launches below fail at different sampled steps, under different tripwire
registration settings; they do not establish a deterministic window trigger.

For a matched follow-up to that reference, [b4] remains useful: the 19 GiB arena
([§6](#6-worked-around-expandable_segmentstrue-caps-vram-at-19-gib)) shapes
*where* a wild store lands, so unsetting it is both a fix on its own merits and
a perturbation of reading (2).

### 3.1 What the reproducer shows

**September 18 validity audit — this qualification applies to the historical
probe tables and conclusions throughout §3.** The recorded GPU faults and
forward-output observations remain observations of the workloads that ran.
The passes do not establish production gradient correctness or attribute
either training NaN to a kernel, overlap mechanism, or compiler defect:

- `repro_gfx1250_nondeterminism.py` created a differentiable input clone

  `xg.grad` remained `None`, the comparison was empty, and historical
  **“dx bit-exact” / backward PASS claims are invalid**. The call now
  passes `_x=xg` and rejects a missing gradient; old results are not

- That script and `repro_gfx1250_hstu_layer.py` unpacked
  `hstu_preprocess_and_attention` as `(attn, u, ...)`, whereas its return

  concatenation/projection, activation, dropout, recomputation, target
  masking and length-sorting settings from the production `STULayer`.
  Production-sized dimensions alone therefore do not make them faithful
  training replays.
- The explanation that weight-gradient differences were harmless atomic
  reordering cited RMSNorm and group-norm kernels, but those are not the
  weighted layer-norm/private-partial-reduction paths exercised here.
  That explanation and the claimed input-gradient agreement do not rule
  out a gradient defect; the actual dispatched reductions must be checked.

| IH client | `27 (GC_UTCL2)` | The graphics L2 translation unit raised it — a shader memory access, not DMA or display |
| UTCL2 client ID | `TCP (0x8)` | The vector/texture data cache — i.e. a **vector memory instruction in a kernel** |
| **`RW`** | **`0x1`** | **A write.** This is the single most diagnostic field: the kernel stored somewhere it should not have |
| `MAPPING_ERROR` / `WALKER_ERROR` | `0x0` / `0x0` | The address **translated fine**; the page simply is not writable by this process. So it is a plausible-looking but wrong address, not garbage |
| `PERMISSION_FAULTS` | `0x5` | Write to a page without write permission |

**`GC_UTCL2` / `TCP (0x8)` / `RW: 0x1` is the same triple** as the original step-212
e2e fault and as the `_weighted_layer_norm_fwd` int32 wrap in
[§5](#5-fixed-an-int32-address-wrap-in-triton_layer_normpy-b3) — both confirmed wild
stores. That is the basis for calling this one a wild store too.

### 3.6 The contention bug found alongside — real, but not the `nan`

A second, genuine defect surfaced while chasing this, and it is **not** the `nan`:
**concurrent high-VGPR GPU work corrupts or faults other GPU work on this host.**

| Aggressor | GFX | Victim: distinct outputs / 20 identical calls | Worst error |
|---|---|---|---|
| none (idle) | 0 % | **1** — 120/120 clean, 3 procs, both paths | — |
| bf16 GEMM + gather, 150 GiB | 100 % | ~1 event in 420 calls | 1.3e-05 |
| **Triton HSTU fwd+bwd, separate process** | 100 % | **7, 9, 7 → ~35 % of calls wrong** | **1.8e-01** |

- **Not "the GPU is busy"** — both aggressors pin GFX at 100 %; only the high-VGPR
  one corrupts, 175x more often. This is a0 defect **[7] high-VGPR + concurrent
  streams**, now with a rate and a reproducer.
- **Not a Triton bug** — under the HSTU aggressor **PyTorch is the worse victim**.
  The victim path is incidental.
- **Not latched** — it clears the moment the aggressor stops, and the correct
  answer is bit-identical before and after. **Do not AC power-cycle for this one**;
  that was [§7](#7-if-gather-corruption-returns-the-ac-power-cycle), a
  different bug.
- **Why it is not the 1370 `nan`:** the e2e is single-stream.
  `train_loop()` takes `use_pipeline: bool = False`
  ([`train/utils.py:1720`](../../generative_recommenders/dlrm_v4/train/utils.py)),

### 3.8 Register pressure in `_hstu_attn_bwd`: measured, and not the mechanism

`ops/triton/triton_hstu_attention.py` already carries a gfx1250 workaround, and its
comment describes our exact symptom:

> `BLOCK_N=128 reaches the 1024-VGPR ceiling and intermittently corrupts a store address. 64 uses 758 VGPRs without spilling.`

So somebody had already tied a wild store in this kernel to register pressure, and
pinned `BLOCK_N=64`. We still fault with that pin in place. Measured with
[`scripts/probe_gfx1250_bwd_vgpr.py`](../../scripts/probe_gfx1250_bwd_vgpr.py),
which reads `.vgpr_count` / `.vgpr_spill_count` / `Occupancy` out of the cached
AMDGCN assembly (Triton's `.json` metadata carries no register counts):

| `BLOCK_N` | VGPRs | VGPR spills | SGPR spills | Occupancy | Two-stream 400 k arm |
|---|---|---|---|---|---|
| 64 (the current pin) | **917** | 0 | 0 | 1 | **FAULT**, 3/3 in ~25 s; 2/2 again here |
| 32 | **760** | 0 | 0 | 1 | **FAULT**, 2/2 within 600 s |

Two things follow, and they point in opposite directions.

**The pin looks one step short of its own intent.** On this toolchain `BLOCK_N=64`
compiles to **917** VGPRs — 90 % of the 1024 ceiling — not 758. The config that
actually lands on ~758 is `BLOCK_N=32`, at **760**. Whoever wrote that comment
appears to have measured 32 and pinned 64.

**But fixing that does not fix the bug.** `BLOCK_N=32` still faults 2/2. Cutting
register pressure 917 → 760, with zero spills and unchanged occupancy in both cases,
does **not** suppress the corruption. So **register pressure alone is not the
mechanism**, the existing workaround is not a fix for this defect, and the
"high-VGPR" half of a0 defect **[7]** is weakened as an explanation — concurrency,
not register count, is carrying the effect ([§3.2](#32-what-we-conclude)
conclusion 3).

`HSTU_BWD_BLOCK_N` was added to that file as an env override so the sweep can be
repeated without editing source:

```bash
EXTRA=HSTU_BWD_BLOCK_N=32 gr repro_gfx1250_fast_fault.py --rows 400000 --streams 2
```

**A trap worth knowing.** A GPU fault here can write a coredump the size of the
process. One of these runs filled the host filesystem. Pass
`-e HSA_ENABLE_COREDUMP=0` unless you specifically want the dump.

### 5.2 What it is: the same class as [3], in a different file

`generative_recommenders/ops/triton/triton_layer_norm.py` computes row addresses
in **int32**. The pattern, verbatim from `_weighted_rms_norm_fwd`:

```python
rows = start_row + tl.arange(0, BLOCK_N)     # int32
row_mask = rows < N                          # bounds check on the UNWRAPPED id
x_block = tl.load(
    X + rows[:, None] * stride_x + cols[None, :],   # address from the WRAPPED product
    mask=mask_2d, other=0.0,
)
```

This is [3]'s exact signature: **the bounds check and the address are computed
from different values.** `rows < N` passes, while `rows * stride_x` has already
wrapped negative, so the masked access is *enabled* and lands ~8 GiB below the
tensor.

**Thirteen un-widened sites, while the same file widens elsewhere** — [3]'s
"neighbours widen, this one doesn't" tell:

| Kernel | Un-widened `rows[:, None] * stride_*` | Note |
|---|---|---|
| `_layer_norm_fwd` (:109) | `:134`, `:164` | |
| **`_weighted_layer_norm_fwd`** (:175) | **`:208`, `:242`** | **on the HSTU path** (`ops/hstu_compute.py:106`); **reproduced below** |
| `_weighted_layer_norm_bwd_dx` (:297) | `:342`, `:347`, `:385`, `:398` | |
| **`_weighted_rms_norm_fwd`** (:790) | **`:817`, `:839`** | a0 flagged this one **by name** as unprotected |
| `_weighted_rms_norm_bwd_dx` (:846) | `:954`, `:959`, `:988` | |

Already widened in the same file: `row.to(tl.int64)` at `:265`–`:267`, `:865`–`:867`,
and `pid.to(tl.int64)` at `:410`–`:411`.

### 5.3 The reproducer — confirmed, to the row and to the byte

### 5.4 What the reproducer does *not* establish

Stated plainly, because it is the one gap between this defect and the NaN:

- **Whether production reaches `N > 4,194,304` was the open question — and the
  e2e A/B in [§5.5](#55-the-fix) now says it does.** An int64 widening is a
  *no-op* unless something exceeds int32, and it changed the outcome at step 300,
  so something did. The reconciliation with a0's `N ≈ 2.74M` is that **jagged `N`
  varies per batch**: sequence lengths differ, so `total_rows` is not fixed, and a
  corpus *average* says nothing about the tail. The wrap fires on whichever batch
  first exceeds 4,194,304 rows.

  This also explains the **wandering onset** (a0 saw step 91 vs ~190 under an
  identical seed) better than the allocator-accident story does: it is which
  *batch* is large enough, not which tensor happens to sit below `Y`.

  Still worth measuring `N` directly — but for its **maximum and distribution**,
  not its mean. `N` is known by step 1, so a ~5-step instrumented run answers it.
- **A tempting coincidence that does *not* hold up:** `1024 × 4096 × 512 = 2**31`
  exactly, i.e. `BATCH_SIZE × MAX_SEQ_LEN` *is* the wrap row. But there is **no
  `jagged_to_padded` conversion on the HSTU path** — `layer_norm` receives the
  jagged `[total_rows, D]` tensor, with 1.53× margin. This was the leading
  candidate and the arithmetic does not support it.
- **The reproducer faults; production NaNs.** Not a contradiction — it faults only
  because in a small probe the memory 8 GiB below `y` is unmapped. In the
  training process, holding ~150 GB, that address lands in **live allocations**,
  so the wild store poisons rather than faults. That silent-poisoning asymmetry
  is [3]'s recorded signature.
- The 6 GiB canary was too small to catch an 8 GiB-below access. Catching the
  silent case needs a canary **> 8 GiB allocated *below* `y`** — and this
  allocator hands out *descending* addresses, so the canary must be allocated
  *after* `y`, which means driving the Triton kernel directly instead of through
  the wrapper.
- **`rms_norm` and `N = WRAP + 100_000` were never run** — the script aborted at
  the first fault.

### 5.4b Why a0's [3] fix did not already cover this

a0 fixed this **defect class** and the fix **is** in the repo — commit `1a3dcd6`,
*"Fix int32 row-offset overflow in `_ln_mul_dropout_fwd_rng` (gfx1250 nan)"*. But
`git show --name-only 1a3dcd6` lists exactly one file:
`generative_recommenders/ops/triton/triton_hstu_linear.py`. **It never touched
`triton_layer_norm.py`.**

The commit states its audit was complete — *"The backward kernels were audited …
so the forward was the only defect"* — and that is true **within that file**. The
audit never crossed into `triton_layer_norm.py`, which carries the identical
pattern in five kernels.

**Why a0's run passed anyway: the wrap rows differ by 3×.**

| | kernel | stride | wrap row |
|---|---|---|---|
| a0 fixed (`1a3dcd6`) | `_ln_mul_dropout_fwd_rng` | `3*D` = 1536 | **1,398,102** |
| fixed here ([§5.5](#55-the-fix)) | `_weighted_layer_norm_fwd` | `D` = 512 | **4,194,304** |

At jagged `N ≈ 2.74M`, a0's kernel wrapped on **essentially every batch** — hence
NaN by step ~190, 2/2. `triton_layer_norm.py` needs `N > 4.19M`, so it trips only
on unusually large batches. **a0's 600 clean steps were not evidence that file was
safe; they were the rarer trip not yet happening.** This is a0's own reasoning
from the same commit — *"Batch size enters only by scaling N past the wrap row,
which is why this presents as batch-gated while being a pure row-count bug"* —
simply never applied to the second file.

> **Consequences worth acting on:**
> - The [§5.5](#55-the-fix) fix is **new work, not a re-application**, and
>   belongs upstream. **a0 is exposed to it today** and has only been lucky.
> - a0's `600/600` batch-1024 result does **not** clear `triton_layer_norm.py`,
>   and a0's own ≥3000-step bar was never met for these kernels.
> - a0's doc mentions `_weighted_rms_norm_fwd` repeatedly, but always as a
>   **`clamp_num_stages` coverage gap** (defect [4] — it uses a raw
>   `@triton.autotune`), never as an int32 risk. The two were never connected.

### 5.5 The fix

Widen the row index once per kernel and use it for every load and store — the
same shape as [3]'s fix in `triton_hstu_linear.py:186`:

```diff
     rows = start_row + tl.arange(0, BLOCK_N)
     row_mask = rows < N
+    rows_i64 = rows.to(tl.int64)
     mask_2d = row_mask[:, None] & col_mask[None, :]
     x_block = tl.load(
-        X + rows[:, None] * stride_x + cols[None, :],
+        X + rows_i64[:, None] * stride_x + cols[None, :],
         mask=mask_2d, other=0.0,
     ).to(tl.float32)
```

Apply to all 13 sites in the §5.2 table. Keep `row_mask` on the **narrow**
`rows` — widening the comparison is unnecessary and widening only the address is
the entire point.

Cost is negligible: it is address arithmetic on a `BLOCK_N`-sized vector, once per
tile, not per element.

**APPLIED 2026-09-16** to all 13 sites across all 5 kernels (`rows_i64` is defined
once per kernel, immediately after `row_mask`, and used by every strided load and
store; `row_mask` itself stays on the narrow `rows`).

**Verified against the §5.3 reproducer — the fault is gone:**

| `N` | before | after |
|---|---|---|
| 4,194,303 | PASS | PASS |
| 4,194,304 | PASS | PASS |
| **4,194,305** | **MEMORY FAULT** | **PASS** |
| 4,294,304 | *(never reached)* | PASS |
| **8,388,609** | *(never reached)* | **PASS** — two full wraps |

`bad_rows=0`, `nonfinite=0`, `canary_bad=0` at every size, against a `torch`
reference. **`rms_norm` passes the same sweep** — `_weighted_rms_norm_fwd` is the
kernel a0 flagged by name and it had never been exercised past the wrap before.

**Verified end to end** (`b1024_a30_i64fix_0916_0455`, same `SEED=1`, same

## 6. Worked around: `expandable_segments:True` caps VRAM at 19 GiB

Unrelated to §§5 and 7, found while building the §5 reproducer, and it affects
runs retaining this allocator setting.

Measured by allocating 1 GiB fp32 tensors in a loop inside `triton-7ff97e-test`
(torch `2.11.0+rocm7.14.0a20260625`, gfx1250):

| `PYTORCH_CUDA_ALLOC_CONF` | Result | Peak reserved |
|---|---|---|
| `expandable_segments:True` | **OOM at 19 GiB** | 19.004 GiB |
| *(unset)* | **392 GiB OK** | **399.0 GiB** |

**That is ~5 % of the card.** It is not contention and not partitioning:
`torch.cuda.mem_get_info` reports free = 431.7 GiB / total = 432.0 GiB in *both*
cases, `amd-smi` shows `USED_VRAM: 167 MB` with "No running processes detected"
and no KFD clients, and 256 CUs are visible (so not an XCP slice).

The flag is set in **five** places, including the one the e2e uses:

| Location | |
|---|---|
| [`scripts/run_prod_convergence_1gpu.sh:93`](../../scripts/run_prod_convergence_1gpu.sh#L93) | **the e2e path** |
| `Dockerfile:90`, `Dockerfile.amdprimus0815:137` | container-wide `ENV` |
| `scripts/run_smoke_shrink_1gpu.sh:43`, `scripts/launch_local.sh:73`, `scripts/launch_slurm.sh:610` | |

The e2e trains anyway because fbgemm TBE allocates the ~150 GB of embedding
tables outside the PyTorch caching allocator. But **every torch tensor in the run
is confined to a ~19 GiB arena** — which is also precisely the kind of dense,
fully-live region an 8 GiB-negative wild store would land in. Consistent with
§5's silent-poisoning mechanism; **not evidence for it.**

**Recommended:** re-run the e2e with `PYTORCH_CUDA_ALLOC_CONF` unset. It is a
one-variable change that both removes a demonstrably broken setting and tests
whether the allocator layout is implicated in the NaN.

**September 18 update:** both allocator settings were cleared for the
new-image, start-zero test. The post-reboot baseline still reproduced NaN
at logged step 60, so clearing this setting does not prevent NaN under that
combination. A matched allocator comparison against the September 16
reference is still absent.

## 7. If gather corruption returns: the AC power cycle

**This section replaces a ~400-line investigation that is now closed.** Between
2026-09-12 and 2026-09-16 this host silently returned wrong data from gather
operations. It was **not a software bug**, and the reproducers written to chase
it are no longer useful — they all read clean now. What is worth keeping is the
symptom description and the recovery, because **the defect can come back**.

**What it looked like.** `torch.index_select` returned wrong rows — 82–95 % of
trials bad at `D=16`, 26 % at `D=4` — while **dense GEMM in the same process was
provably clean**. It was not a numerics problem: the values returned were other
rows, verbatim. The e2e died at step 212 with a page fault whose `dmesg`
signature was `GC_UTCL2` / client `TCP (0x8)` / `RW: 0x1`.

**Why it is not software.** It survived **8+ warm reboots**. Four independent
container images corrupted identically, including one carrying a *different LLVM
entirely* (ROCm 7.15 + torch 2.10.0). No image, Triton pin, LLVM or driver
package made any difference.

**What fixed it: a full AC power cycle**, with the software stack completely
untouched — out-of-band via BMC `10.5.217.131` (`ipmitool chassis power cycle`),
or at the rack. Before: 82–95 % bad. After: **0/2000**, **0/1000**, and 0/600 on
all 14 arms of the original reproducer. Remember to reload the driver by hand
afterwards ([§1.3](#13-mandatory-flags-and-boot-procedure)).

> **Do not present the AC cycle as a root-cause fix.** "Latched platform state"
> names the behaviour, not a cause — candidates include UTCL2/TCP translation
> state, a DF/fabric configuration register, an SMU artifact, or a soft error in
> a register outside the warm-reset domain. It is a known-working *recovery for
> an open defect*, and that is the form it should take when handed to the
> driver/hardware team. It is also **n=1 and not cleanly attributable**: two
> cycles happened on 2026-09-16 and the GPU could not be measured between them.

**How to tell whether it is back, and why you should check.** The corruption
rates **grew with uptime** — 14.67 % on 2026-09-12 → 82–95 % by 2026-09-16 —
which suggests accumulation rather than a single upset. So:

```bash
docker exec -e PROBE_ITERS=1000 <container> bash -lc 'cd /tmp && python probe.py'
```

**Run this before trusting any long e2e run, and record host uptime with the
measurement.** A clean `probe.py` is **necessary but not sufficient** — see
[§3.6](#36-the-contention-bug-found-alongside--real-but-not-the-nan), which shows
that a concurrent GPU job on this host can corrupt results on its own. Take the
probe on an **idle** GPU.

**Do not confuse this with the current blocker.** The step-1370 `nan`
([§2](#2-the-open-blocker-train_lossnan-at-step-1370)) appeared *after* the AC
cycle, on a host whose gather path reads 0/2000 clean. **An AC cycle is not a
remedy for it** — §3.6's contention effect, unlike this one, is not latched and
clears by itself when the competing job stops.

# Bring-up on MI450 A0 (gfx1250, single GPU)

The yambda-5b HSTU ranker on an **MI450 A0 engineering sample**, one GPU.
**Scope: batch 1024 at `START_TS=0`.** That is the configuration MLPerf scores
and the only one maintained here. Batch 128 and batch 8 are retired, and every
`START_TS=150` run is kept as defect evidence only — [1.1](#11-where-this-stands).

> **THE LIVE BLOCKER**
>
> **`train_loss=nan`.** At the scored configuration — `START_TS=0`, batch 1024 —
> the loss goes non-finite at **global step 5-11**, in one loss term, before
> `backward()`, and never recovers. It is **nondeterministic**: two
> byte-identical uninstrumented runs on the same boot agree to every printed
> digit through step 9 and then diverge, one finite and one `nan`. Current hit
> rate **1 in 2 runs at ~90 s per run**. No fault, no traceback, clean `dmesg`.
>
> A second `nan`, at step **1340** (a0) / **1370** (b0), is recorded under a
> different start point. The two are **not yet known to be the same defect**.
>
> **Everything about this is in [2](#2-the-live-nan), which is where to start.**

**The rest of this document is the bring-up record that got to that point**, and
it is worth stating plainly what it bought — and what it did not. As of
**2026-09-10 the model trains end to end on Triton kernels at the production
batch size, 1024**: 600/600 steps, 60 logged losses, zero non-finite, `EXIT=0`,
**reproduced twice, independently, across an `amdgpu` driver reload**
([4.1](#41-the-confirming-runs)). That result stands as reported, but it was run
at **`START_TS=150`**, which skips the warm-up windows and is **not** an
MLPerf-valid start point — as was every other clean run in this document. At
`ts=0`, the start point MLPerf actually scores, there is **no clean result at any
length**. See [1.1](#11-where-this-stands).

That took workarounds for six Triton/LLVM defects ([1], [2], [4], [4c], [5], [6]),
three fbgemm patches for wave32, a table shrink to fit one GPU, and **one genuine
source fix** — [3], an int32 row-offset overflow in this repo's own kernel
([row 15 of §5](#5-changes-applied-to-master)). **None of it is in the benchmark's math**, and none of
it is yet known to explain the `nan`.

**This is functional bring-up at one configuration, not convergence.** The MI350
reference converges to target across 60 runs; 600 steps at batch 1024 is ~1/3.7 of
the way to that reference's *first* eval checkpoint. Read
[1.2](#12-against-the-mi350-reference) before quoting the result.

The working stack is upstream Triton
[`7ff97e3109`](https://github.com/triton-lang/triton/commit/7ff97e310935b4a79794878dbc911f9af25d38d9).
Everything about 3.6.0, AMD 3.7.1 and AMD 3.8.0 is **reference only** and lives in
[10. Historical](#10-historical-earlier-triton-versions). Branch `chcai/mi450_a0`;
companion to [`training_recipe.md`](../training_recipe.md) and
[`perf_opt.md`](../perf_opt.md).

## 1. Status

### 1.1 Where this stands

**Only `START_TS=0` counts.** An official MLPerf run starts at ts=0, so that is
the only start point at which a result on this stack means anything about the
benchmark. **Every result at that start point is a failure**, and it is
[2](#2-the-live-nan).

| MLPerf-aligned configuration | Steps | Samples | Result | Runs | Log |
|---|---|---|---|---|---|
| **Batch 1024, `START_TS=0`** | 20 attempted | 20,480 | **`nan` at global step 5-11**, nondeterministic, absorbing | **1 `nan` / 2 valid runs** | `runs/nan_onset_0917i/`, `runs/b1024_nantrip_ts0_0917{c,d,e}.log` |

That is the whole table. There is no clean `START_TS=0` result at any length:
the longest run that stayed finite reached step 20, and its sibling on the same
boot went `nan` at step 10.

**Everything else in this document ran at `START_TS=150`** — the gin's
"skip the near-empty warm-up windows and begin at a dense window" shortcut
(`yambda_5b.gin:575-579`). That was a deliberate bring-up convenience and it is
**not** an MLPerf-valid start point. Verified from the logs: `b1024_fixed`,
`b1024_fixed_rep2`, `b1024_rep2`, `prod_b1024_smoke`, `nan128/long1`,
`retest_0910/pipe_b1024_r1`, `smoke_7ff97e_pr7` and
`b1024_c07_i64fix_0916_2243` all log `train_ts=150`.

Those runs are **retained as defect evidence, not as results.** They are what
proved defect [3]'s fix, what priced the workarounds in
[5](#5-changes-applied-to-master), and what the [6.1](#61-re-test-queue) queue is
written against — deleting them would delete the evidence chain. They may not be
quoted as a statement about the benchmark.

| `START_TS=150` — evidence only, **not** an MLPerf result | Steps | Result | Runs | Log |
|---|---|---|---|---|
| **Batch 1024 — the ≥ 3000-step bar** | **1340 of 3000** | **`nan` at step 1340**, and at every logged step to 2210 | **0 / 1** | `runs/b1024_c07_i64fix_0916_2243.log` |
| Batch 1024, 600 steps | 600 | clean, `train_loss` 0.13826 | 2 / 2 | `b1024_fixed.log`, `b1024_fixed_rep2.log` |
| Batch 1024, **pipelining unclamped** | 600 | clean, `train_loss` 0.13833, **2.8 % slower** | 1 | `retest_0910/pipe_b1024_r1.log` |
| Batch 1024, **before** the [3] fix | ≤ 200 | `nan` at step 91 and ~190 | **0 / 2** | `prod_b1024_smoke.log`, `b1024_rep2.log` |

**The `START_TS=150` table also fails its own bar.** This doc's bar for calling a
stack clean is **≥ 3000 steps** ([10.2](#102-defects-by-version), row 3: AMD
3.7.1 looked fixed at 250 steps and went `nan` at 2200). The ≥ 3000-step run was
[6.1](#61-re-test-queue) rank 8, was run on 2026-09-16, and went `nan` at step
1340 — then stayed `nan` for every logged step to 2210, where it was stopped by
hand (`EXIT=143`; not carried to 3000). So the clean rows above it are clean only
because they are short.

**What the clean `START_TS=150` rows do still establish**, stated narrowly: the
kernels compile, the model runs forward and backward at the production batch
size, and the loss tracks the PyTorch-kernel reference. That is functional
bring-up of the stack. It is **not** a result at the scored configuration, and
until [2](#2-the-live-nan) is closed there is no such result.

**The [3] fix is untouched by any of this.** It is still proven by its own
deterministic reproducer, and its pre-fix onsets (91, ~190) are 7–15× earlier
than step 1340. The live `nan`s are different defects that 600 steps was simply
too short to see.

**Neither live `nan` is an a0 defect.** The step-1340 failure is recorded on the
**b0** host at step **1370**
([`mi450_b0.md` §2](../mi450_b0/mi450_b0.md#2-the-open-blocker-train_lossnan-at-step-1370)),
from a run matched on every controllable variable — same seed, same batch, same
container, same Triton pin, same source. Two boards, 30 steps apart. Whatever it
is, it is in the **shared gfx1250 / ROCm / Triton stack**, not in either board.
Full comparison in [2.2](#22-the-long-run-nan-at-step-1340-a0-and-1370-b0).

### 1.2 Against the MI350 reference

**These are two different categories, not two scores on one scale.** MI350 is
**convergence-validated**: [`rcp_logs/`](../../rcp_logs) holds 60 MLPerf logs,
`submission_platform: MI350`, closed division, at global batch 8192 / 16384 /
32768 with 20 seeds each — **60 of 60 reach the 0.75 AUC target**. MI450 A0 is at
**single-configuration functional bring-up**: the configuration completes and its
loss matches the PyTorch-kernel reference. It makes **no quality claim**.

| | MI350 (RCP) | MI450 A0 today |
|---|---|---|
| Global batch | 8192 / 16384 / 32768 | **1024** — 8× below the smallest RCP point |
| Samples | 69M to reach 0.75 at gbs 8192 (112M at 32768) | **614,400** |
| Eval AUC | 0.7636–0.7875, 60/60 runs ≥ 0.75 | **0.4994** — chance |
| Seeds | 20 per batch size | 1 (2 runs, same seed) |

For scale: **this run is ~1/3.7 of the way to MI350's *first* eval checkpoint**,
which itself reads `0.5010`, and ~1/112 of samples-to-target at gbs 8192. It is
not a short convergence run; it is shorter than the reference's first datapoint.

**Batch size is no longer the blocker — the start point is.** The previous
edition recorded the gap as blocked on batch size, because batch 128 `nan`'d in 3
of 4 runs. That is cleared: batch 1024 runs 2/2 clean over 600 steps. But every
one of those runs was `START_TS=150`, and at `START_TS=0` — the only start point
MLPerf scores — the loss goes `nan` by global step 5-11
([2](#2-the-live-nan)). The remaining distance is **not** machine time; it is a
live defect that has to be root-caused first.

Two things that cut opposite ways, since readers assume the wrong one:

- **Stronger than "it didn't crash."** The full Triton op set compiles and
  dispatches, and at batch 8 `train_loss` is `0.10000` against the
  PyTorch-kernel reference's `0.1015` — numerics agree with the reference
  implementation at the working point.
- **Weaker than "functional."** That point needs workarounds for six Triton/LLVM
  defects, three fbgemm wave32 patches and a 4× table shrink. None touch the
  benchmark's math, but three **narrow the configuration space instead of fixing
  anything**: pipelining clamped to `num_stages=1`, `BLOCK_N` pinned to 64,
  buffer ops off.

**This is A0 engineering silicon** and at least [6] is an A0 hazard, so some of
the gap may not exist on B0. That split is unmeasured.

Throughput is not comparable yet either, for an unrelated reason: there is no
matrix-core GEMM path for gfx1250, so HFU reads ~1 % (see
[9.3](#93-performance)).

Ladder, if you need one for tracking: compiles → op-level correctness →
**single-config e2e completes at production batch (MI450 today)** →
benchmark-valid config, multi-GPU → **convergence to target (MI350)** →
competitive throughput.

### 1.3 What it does not establish

| Claim a reader might infer | Why it is not established |

Eval AUC `0.4994` is chance and is **not a symptom of anything**; it says the eval path runs and returns a finite metric. `run_stop status="aborted"` is the MLPerf convergence verdict, reported by *every* run in this document, clean or not — not a failure signal |
| The stack is clean | **No — two `nan` defects are open** ([2](#2-the-live-nan)). At the **scored** start point `START_TS=0` the loss goes non-finite at global step **5-11**, nondeterministically, ~1 run in 2 ([2.1](#21-the-ts0-nan-nondeterministic-onset-step-5-11)) — that is the blocker. Separately, **the ≥ 3000-step bar was run at batch 1024 on 2026-09-16 and failed**, going **`nan` at step 1340** ([1.1](#11-where-this-stands), [2.2](#22-the-long-run-nan-at-step-1340-a0-and-1370-b0)). [3]'s mechanism is still fixed — proven by a deterministic reproducer — but **a second, distinct `nan` defect is open**, reproduced on b0 at step 1370 |

Not an MLPerf-valid configuration, and the vocabulary change means accuracy is not comparable to the RCP reference **even in principle** |

| The hang class is fixed | **Avoided, not fixed.** [1b] shows hangs that survive the knob |
| The workarounds are free | **One of three is measured, and it is not the big one.** Row 3 has an e2e number and it favours the workaround — the clamp is **2.8 % faster** at batch 1024 ([6.3](#63-cost-of-the-workarounds-still-in-place)). Row 2 is kernel-level only (1.54× slower); no e2e number, because `BLOCK_N=128` faults. **Row 1 — buffer ops off for every kernel — has no number at all and cannot get one on this host**, since the A/B needs the dispatch that hangs. It is the largest unpriced item in the document ([6.1](#61-re-test-queue), rank 1) |

## 2. The live nan

**This is the active investigation.** `train_loss` goes non-finite in two places
that are **not yet known to be the same defect**:

| | start point | onset | reproducibility | state |
|---|---|---|---|---|
| [2.1](#21-the-ts0-nan-nondeterministic-onset-step-5-11) **ts=0** | `START_TS=0` | global step **5-11** | **nondeterministic** — 1 `nan` in 2 valid runs, ~90 s per run | **Live, primary** |
| [2.2](#22-the-long-run-nan-at-step-1340-a0-and-1370-b0) **long-run** | `START_TS=150` | step **1340** (a0), **1370** (b0) | 1 of 1 per host, never re-run | Live |

Two earlier `nan` episodes are closed or retired and are kept for reference
only: the batch-128 `nan` on Triton 3.6.0 / 3.7.1 ([10.4](#104-the-batch-128-nan-on-360--371)) and the
batch-8 pipelining `nan` ([10.5](#105-the-batch-8-pipelining-nan-4-pre-fix-stack)). The one `nan` that **was** root-
caused and fixed is [3], the int32 row-offset overflow
([row 15 of §5](#5-changes-applied-to-master)); its onsets were step 91 and ~190, 7-15x earlier than
2.2, and it is proven fixed by its own deterministic reproducer.

**2.1 is what is being worked**, for two practical reasons:

- **Cycle time.** It reproduces in ~90 seconds. 2.2 needs ~4 hours to reach its
  onset, which makes hit-rate statistics unaffordable and turns every
  instrumentation experiment into a day.
- **Fidelity.** Official MLPerf runs start at `ts=0`, so 2.1 sits at the
  configuration that is actually scored. 2.2's `START_TS=150` skips the warm-up windows
  entirely, so it is not a benchmark-valid start point at all — see
  [1.1](#11-where-this-stands).

**What is established about 2.1** — measured, not inferred:

- **Non-finite before `backward()`**, in exactly one loss term (`listen_plus`);
  the capture hook reports `other terms finite: []`.
- **Absorbing.** 240 consecutive `nan` steps with no recovery, across window
  boundaries.
- **Not divergence.** At global step 5-11 the 24,000-step warmup has the LR at
  ~1e-9 and the weights are essentially at initialisation.
- **Nondeterministic**, from two byte-identical uninstrumented runs on one boot
  ([2.1.1](#211-nondeterminism-established-series-nan_onset_0917i-2026-09-17)).

**What is not established:** which component manufactures the value; whether it
comes from forward compute or from a weight written during the previous
backward; whether 2.1 and 2.2 share a cause ([2.3](#23-are-21-and-22-the-same-defect)); and whether any
defect already recorded in [7.1](#71-defect-record) explains either.

**Consequence for a handoff.** Because the onset wanders, there is no fixed bad
input and no single batch anyone can be handed. The deliverable is a **hit rate
plus a named component**, not a deterministic script — [2.5](#25-what-runs-next).


### 2.1 The ts=0 nan, nondeterministic, onset step 5-11

**Configuration.** `START_TS=0` (the official start point), batch 1024, one GPU,
per-step loss logging. Three runs on 2026-09-17: `b1024_nantrip_ts0_0917c/d/e`.

**What the `nan` is.** Established across those three runs, and none of it is
inferred:

- **Forward-side.** A non-finite term is present in `aux_losses` *before*
  `backward()` is called, so it is not the optimizer and not a prior step's
  update.
- **Single term.** `listen_plus` is the only key that goes non-finite; the
  capture hook reports `other terms finite: []`.
- **Absorbing.** 240 consecutive `nan` steps in run d with no recovery, across
  window boundaries. It never comes back.
- **Not divergence.** Onset is at global step 5-11, where the 24000-step warmup
  puts the LR at ~1e-9 and weights are still essentially at initialisation.

**Window/batch map.** `drop_last` discards any window with fewer than 1024
anchors, which matters because the early windows are tiny:

| step | window | batch_idx |
|---|---|---|
| 1-3 | w0 (3,411) | 0,1,2 |
| 4 | w1 (1,944) | 0 |
| — | w2 (885), w3 (121), w4 (41) | **dropped entirely** |
| 5 | w5 (1,694) | 0 |
| 6-12 | w6 (7,888) | 0-6 |

Because those three windows never form a batch, a "degenerate tiny batch" is
**not** available as an explanation, and an earlier suspicion along those lines
is withdrawn.

**The finding: same input, different output.** Runs d and e are bit-identical
through step 4 (`0.15267`, `0.14412`, `0.13741`, `0.13770`), so both reach w5
batch 0 as step 5 with the same data. Run d computed that batch as **`0.13889`**.
Run e computed it as **`nan`**.

*The caveat that made this provisional — now closed by [2.1.1](#211-nondeterminism-established-series-nan_onset_0917i-2026-09-17).* The two runs did not carry
identical instrumentation: run e's capture hook called `torch.isfinite` on the
loss each step, forcing a device sync run d did not have. A sync cannot change
the mathematics of a computation, so on either reading this is compute
nondeterminism — but the runs were not byte-identical, so the onset distribution
was re-measured with N byte-identical short runs
(`scripts/nan_onset_repeat.sh`), and the nondeterminism is established without the confound.

**Unexplained.** `scripts/nan_tripwire.py` patches `torch.Tensor.backward`
unconditionally, and the trainer calls `backward()` on the very tensor that logs
as `nan`, yet `!! FIRST NON-FINITE LOSS` never printed and `NAN_TRIPWIRE_FATAL=1`
never raised. No explanation is offered here.

**Not claimed.** That this is defect [3], the wild-store class, or any other
entry in [6](#6-open-items). They are carried as separate hypotheses. Note that
instrumentation moved onset *earlier* (11 to 5), which is the opposite of the
documented sync-suppression signature.

**State: Live.**

#### 2.1.1 Nondeterminism established (series `nan_onset_0917i`, 2026-09-17)

The run-d-vs-run-e comparison above was confounded: the two runs differed in
instrumentation. `scripts/nan_onset_repeat.sh` removes that confound by running
N times with byte-identical config -- run-d baseline, per-step loss logging only,
no capture hook, `NUM_TRAIN_TS=8`, eval off. Result:

| run | onset | last step | wall |
| --- | --- | --- | --- |
| i01 | none | 20, all finite | 104 s |
| i02 | **10** | 10 | 84 s |
| i03 | -- | 0 | wedged at startup, see [9.1](#91-hardware-and-recovery) |

i01 and i02 agree at every printed digit through step 9 and then diverge:

```
step 9   i01 0.13576   i02 0.13576
step 10  i01 0.13591   i02 nan
```

Same boot, same config, neither instrumented. **The nan is nondeterministic.**
Run e's `.item()` is no longer needed to explain anything, and the
instrumentation-artifact hypothesis for the 11-vs-5 difference is retired.

Divergence points observed across all runs to date: step 5 (d vs g), step 10
(i01 vs i02), step 17 (g01 vs i01). The onset wanders, so there is no fixed bad
input and no single batch that can be handed to anyone as a reproducer. The
realistic deliverable is a hit rate, not a deterministic script. Current rate:
**1 nan in 2 valid runs at ~90 s per run.**

**Correction to 2.1.** That section called runs d/e "bit-identical through step
4". They agree to the five decimals the logger prints, which is a weaker claim;
a perturbation of ~1e-5 is invisible at that precision. This also explains why
i01/g01 re-agree at steps 18-20 after differing at step 17 -- at LR ~1e-9 the
weight delta from a 1e-5 loss difference is far below print resolution. Baseline
run-to-run jitter of ~1e-5 is present and is consistent with ordinary
non-deterministic reduction order (atomics in the fused TBE update, split-k).
That jitter is not itself the defect; what is unexplained is why it occasionally
becomes a `nan`.

**Correction to the "forward-side" claim.** 2.1 infers "forward-side" from
`aux_losses` being non-finite before `backward()`. That establishes the value
existed at the end of step N's forward. It does **not** establish that step N's
forward compute created it: the fused TBE embedding optimizer updates weights
*during backward*, so step 9's backward could have written a non-finite weight
that step 10's forward merely gathered. Loss finite at 9 and `nan` at 10 fits
that equally well. Distinguishing the two requires checking parameters, not just
activations -- see `NAN_MODULE_PROBE_PARAMS` in
`scripts/nan_module_probe.py`. Until that runs, "forward-side" should be read as
"present at end of forward", not "produced by the forward".

**State: Live.**

#### 2.1.2 Deterministic metric blow-up at step 8, and a false convergence signal

Separate from the `nan`, and deterministic -- it reproduces identically in every
run including the ones that never produce a `nan` (g01, i01, i02):

```
step 7   window_ne=2.4549       window_auc=0.5574
step 8   window_ne=6.7943e+11   window_auc=0.9912
step 9+  window_ne=6.79e+11     window_auc=0.5000   (pinned, never recovers)
```

At step 8 the `listen_plus` metric accumulator gains eleven orders of magnitude
and `window_auc` spikes to 0.9912, which fires

```
REACHED AUC>=0.75 on metric/window_auc/listen_plus=0.991196 at elapsed_sec=69.63 step=8
```

-- a **false convergence signal**. In a scored run that is a spurious early
terminate claiming the target was met. Afterwards AUC is pinned at exactly
0.5000 and `gauc` reports 0 samples throughout.

Because it is deterministic it is not the `nan`'s precursor; an earlier reading
of it as one is withdrawn. Whether the two share a root cause is **not known**.
Not investigated further yet.

**State: Live.**

**What it establishes.** The defect is in the **shared gfx1250 / ROCm / Triton
stack**, not in either board. `mi450_b0.md` §1.1 records that a0 and b0 cannot be
told apart through PCI or VBIOS — same device rev `0x00`, same SKU `M4500001` —
and that a0's firmware is unrecorded, which left "different stepping" as an
explanation that investigation could not test. **It no longer needs to be
tested.** Two boards fail 30 steps apart, so board revision and firmware both
drop off the candidate list, and b0's 2026-09-15 firmware update is exonerated.

**What it does not establish, and the honest limits of this comparison:**

- **It does not tell us the onset wanders.** A 2.2 % difference across two hosts
  is *suggestive* that the onset is not a fixed arithmetic cliff — under
  `SEED=1` the data order is identical, so a data-keyed int32 wrap of `[3]`'s
  shape should fire at the **same** step on both. But a cross-host difference is
  weaker evidence than a same-host one, and the two hosts were **not** matched on
  timing (below). The clean discriminator is a **second a0 run at `SEED=1`**,
  which is now the top open item.
- **The hosts differed 1.7× in throughput** — a0 ran 308–327 samples/s against
  b0's 555, with `fill` 46–55 % and `mfu` 3.1–3.3 %, i.e. the input pipeline was
  starving the GPU here. Since `mi450_b0.md` §3.2 conclusion 3 establishes that
  **forward/backward overlap is required** for the fault, the two runs were
  executing under materially different overlap duty cycles. That the onsets still
  land within 30 steps argues the trigger is step- or data-driven rather than
  timing-driven — but it also means "the only difference was the host" is true of
  the *configuration*, not of the *execution*.
- **This run carried the `[b3]` int64 layer-norm widening**
  ([`mi450_b0.md` §5](../mi450_b0/mi450_b0.md#5-fixed-an-int32-address-wrap-in-triton_layer_normpy-b3),
  commit `2d68965`), which a0's 2026-09-10 600-step runs did **not**. It is a
  strict widening that changes behaviour only above row 4,194,304, and both
  code states are clean at 600 — but the 600-vs-1340 comparison is formally
  across two source states, not one.

**Consequences for the rest of this document.** The two 600-step runs in
[4.1](#41-the-confirming-runs) remain correct as reported; what changes is what
may be **inferred** from them. "Batch 1024 is the working point" is true only up
to ~1330 steps. Any future claim resting on run length has to cite this section.

### 2.3 Are 2.1 and 2.2 the same defect?

**Not established, in either direction.** What can be said:

**For one defect.** Both are `train_loss=nan` with no fault, no traceback and a
clean `dmesg`; both are absorbing; both survive across window boundaries; both
appear on a stack whose only known silent-corruption class ([3]) is fixed. A
single rare event whose probability is roughly uniform per step would produce a
step-5-11 onset at `ts=0` and a step-1340 onset later only if the per-step rate
differed by ~100x, which the shapes do not obviously supply — so this argues
*against* a single uniform mechanism rather than for it.

**Against one defect.** The `ts=0` onset lands where the LR is ~1e-9 and the
weights are at initialisation; the step-1340 onset lands after 1.37 M samples of
real training. The two start points also feed different data: `START_TS=0` runs
the tiny early windows ([2.1](#21-the-ts0-nan-nondeterministic-onset-step-5-11)'s window map), `START_TS=150` never
sees them.

**Not tested.** The single experiment that would separate them is a `START_TS=0`
run carried past step 1340, and a `START_TS=150` short run repeated N times.
Neither has been done. Until then they are carried as **two hypotheses, not
one**.

### 2.4 Instrumentation and harness

The measurement apparatus, and the constraints that shaped it. This is
consolidated here because it was previously only in script headers.

**The Heisenbug constraint.** Run e's per-step `.item()` on the loss moved the
observed onset from step 11 to step 5. A sync cannot change the mathematics of a
computation, so this is evidence about *scheduling sensitivity*, not about the
instrument being wrong — but it does mean **a probe that synchronizes cannot be
trusted here**. Every instrument below is built to avoid syncs on the step path.

**`scripts/nan_onset_repeat.sh`** — runs N byte-identical short runs and reports
per-run onset. Design points that are load-bearing:

- **`NUM_TRAIN_TS=8`, eval off.** Eval on the full holdout is 2,058,204 anchors
  and costs ~17 min; with eval on, a 90 s experiment becomes a 20 min one.
- **Unique `RUN_NAME` per run.** `RUN_NAME` drives
  `CKPT_PATH=/data/mlperf_dlrm_v4/ckpt_$RUN_NAME` and **the trainer auto-resumes
  from whatever it finds there.** Leaving the default meant one series wrote an
  end-of-window checkpoint at `train_ts=7` and the next series read it, logged
  `Resume target already reached (end_ts=8, start_ts=8) -- skipping straight to
  final eval`, ran **zero train steps**, and would have scored every run
  "clean". A `RESUME_BUG` guard now aborts on that line, and each run's
  checkpoint directory is deleted afterwards. The default `RUN_NAME` is also the
  *production* convergence run's checkpoint directory, which throwaway runs have
  no business writing into.
- **Early cut.** The harness backgrounds the launcher and polls, cutting on
  `nan`, `STOP_AT_STEP`, a memory-access fault / MES wedge, or `MAX_WAIT`. Before
  this, every run spent ~130 s on an end-of-window checkpoint and >3 min in a
  final holdout eval *after* the last step of interest.
- **`BETWEEN_RUNS_S=30`.** See [9.1](#91-hardware-and-recovery) — relaunch spacing.
- **Persistent `TRITON_CACHE_DIR`.** Cuts the JIT portion of step 0, which is the
  bulk of the wedge exposure window. Pointing it at an *empty* directory makes
  run 1 slower, not faster; the benefit starts at run 2.

**`scripts/nan_module_probe.py`** — module-level device-side non-finite flags,
the instrument built to name the culprit component. `NAN_MODULE_PROBE=1` installs
forward hooks on every module; `NAN_MODULE_PROBE_PARAMS=1` additionally checks
leaf-module parameters, which is what distinguishes "the forward computed it"
from "the previous backward wrote it". Mechanics:

- **Zero syncs on the step path.** Hooks accumulate into device-resident int32
  counters. One `non_blocking` D2H is issued after the forward; the **previous**
  step's copy is read at the top of the next step.
- **Input *and* output are checked**, so the culprit is identified by
  `out_bad=1, in_bad=0` — a module that manufactured a non-finite value rather
  than one that merely propagated it. Rows are ordered by
  `(first_bad_step, execution_rank)` and the earliest qualifying leaf is named.
- **Guarded.** The hook body is wrapped so an instrument can never kill a
  training run; it disables itself with one warning on first error.
- **Explicit negative result.** If nothing has `out_bad=1, in_bad=0`, the probe
  says so — that outcome means the value originates inside a fused kernel whose
  inputs were already non-finite, or upstream of the first hooked module.
- **Coverage checked, not assumed.** `_compute_loss` is a free function, which
  looked like a coverage gap; it runs inside `DefaultMultitaskModule.forward`
  (`generative_recommenders/modules/multitask_module.py:273`), so the hooks do
  reach it.

**Confidence in this approach, stated before the result.** ~35 % that the first
`nan` caught names a clean leaf origin; ~65-70 % within a day's iterations;
~85 % that it narrows the culprit to a component *class*. The four ways it fails:
instrument suppression (the probe perturbs scheduling and the `nan` stops
happening), fused-kernel granularity (the origin is inside one kernel and
"module" is too coarse), stale-weight misattribution (a weight written last
backward, which is what `NAN_MODULE_PROBE_PARAMS` is for), and sharded-parameter
opacity under `DistributedModelParallel`.

**Unexplained, and still open.** `scripts/nan_tripwire.py` patches
`torch.Tensor.backward` unconditionally, and the trainer calls `backward()` on
the very tensor that logs as `nan`, yet `!! FIRST NON-FINITE LOSS` never printed
and `NAN_TRIPWIRE_FATAL=1` never raised. No explanation is offered here.

**Never obtained.** A `last_clean` / `first_bad` tensor pair.

### 2.5 What runs next

Blocked on the host first: the GPU is in an MES wedge. It was *confirmed*
unrecoverable at 06:35 by the two-sample counter test; a repeat at 07:13/07:15
found the counters **flat** (120/109 at both samples) and VRAM drained to 0.2 GB,
so as of 2026-09-17 07:15 it is **probably** still wedged but no longer confirmed
— what remains abnormal is GFX 100 % at 858 W with no process owning the device.
A bare matmul in a fresh container settles it; otherwise an AC power cycle
([9.1](#91-hardware-and-recovery)). After recovery,
`sudo modprobe amdgpu gpu_recovery=0`, verify `initstate=live`, and re-run the
gather probe before trusting any measurement.

Then, in order:

1. **Probe series.** `PROBE=1 NAN_MODULE_PROBE_PARAMS=1`, N ~ 6. At the observed
   1-in-2 rate that should catch 2-3 `nan`s. **Deliverable:** a named component,
   or the explicit negative result above.
2. **Suppressor A/B.** `HIP_LAUNCH_BLOCKING=1` in one arm and an explicit
   `synchronize()` between forward and backward in another. If either arm
   suppresses the `nan`, that is a strong statement about the class.
3. **The d-config A/B.** Re-run run d's exact configuration on the current boot,
   to separate "pre- vs post-AC-cycle" from "`NUM_TRAIN_TS=8` / eval off" as the
   reason the g/h/i series produce fewer `nan`s than d/e did.
4. **2.3's separating experiment** — a `START_TS=0` run carried past step 1340,
   and a repeated short `START_TS=150` run.
5. **[2.1.2](#212-deterministic-metric-blow-up-at-step-8-and-a-false-convergence-signal)** — the deterministic step-8 metric blow-up and the
   false `REACHED AUC>=0.75` convergence signal it fires. Unrelated to the `nan`
   as far as is known, but it is a scored-run correctness problem in its own
   right.
6. **Handoff package** — component + onset distribution + hit rate + A/B table +
   a standalone script. Note that the standalone script cannot be deterministic;
   see [2](#2-the-live-nan).

**What `START_TS=0` actually changes, and what it does not.** The gin says the
first ~130 daily windows are "near-empty warm-up"
(`yambda_5b.gin:574`). It is worth being precise about *which* degeneracy that
is, because the two point at different kernels. At the scored floor
`MIN_HISTORY=4086` an anchor requires a full 4086 prior events, so the rows that
do arrive are **full-length by construction** — ts=0 does *not* produce short UIH
sequences. What it produces is **few anchors per window**: small, possibly empty
batches, an effective batch far below the nominal 1024, and an autotune entry
picked for a shape that is not the shape that arrives (`AUTOTUNE_B =
prev_power_of_2(B)`). So the hypothesis to test is **batch degeneracy, not
sequence degeneracy**.

Cheapest discriminator, and it should run before the `START_TS` sweep: log
per-step effective batch and total jagged `N` for the first 11 steps of a ts=0
run. One line in the probe, and it says which of the two is in play before any
kernel is read.

The broader, non-`nan` re-test queue is unchanged and lives in
[6.1](#61-re-test-queue).

### 3.4 Operating notes

- **`AMDGCN_USE_BUFFER_OPS=0` is the only correctness flag you must pass**, and
  both runners default it. Every other workaround is gated in code on arch and
  Triton version, so it applies itself. `AMD_SERIALIZE_KERNEL=3` is optional and
  costs throughput — leave it off outside debugging.
- **Start from an idle GPU.** A faulted rank and its orphaned dataloader workers
  keep holding HBM, so the next run starts under artificial memory pressure.
  `scripts/bisect_hooks/gpu_cleanup.sh` clears them; check `rocm-smi
  --showmemuse` reads 0 % first.
- **`sudo modprobe amdgpu` after every boot** — the module is blacklisted on the
  kernel cmdline; `/dev/kfd` appears ~15 s later. A container created while
  `/dev/kfd` was absent will not see the GPU: recreate or restart it after the
  modprobe. See [9.1](#91-hardware-and-recovery).
- **A 600-step batch-1024 run takes ~34 min** — ~1.9 min of startup (140 GiB
  table allocation, autotune) then **3.40 s/step** (measured `step_ms` 3397 and
  3403 across the two runs; 3492 unclamped).

### 6.1 Re-test queue

**Two questions, one table.** What is worth running again now that [3] is fixed,
and — since MI450 is supposed to *beat* MI350, not merely complete — **which of
these follow-ups actually give throughput back?** The table is ordered by the
second question: **rank 1 is the largest recovery available, rank 9 the
smallest.** Every defect id is listed, including the Passing ones — a defect whose test
passes is exactly a candidate for *deleting a gate*, which is why they are not
filed separately.

**Set the scale first, or this table will mislead you.** Every workaround here is
second-order against the gap in [9.3](#93-performance): the matrix cores are
idle, measured bf16 GEMM is only **1.46× fp32**, and HFU reads **1.1–1.9 %**.
Reverting *every* row below still leaves the model running on the vector path.
**MI450-versus-MI350 throughput is a BLAS-maturity question, not a
workaround-revert question** — this table is worth a few percent e2e and up to
1.54× on one kernel, against a ~50× denominator that none of it touches.

**Rank is not do-order.** The two largest recoveries are both *blocked* — rank 1
on a reboot that should not be spent, rank 2 on an upstream LLVM fix. The first
thing to actually run is **rank 3** ([4c], already Passing, minutes), then the
validation items at ranks 8 and 9, which buy no throughput but are what this
document's claims rest on.

anyone who needs it, and the widening is what gets upstreamed — but rows 4 and 16

### 7.2 Root cause of the attention-backward fault ([6] / [4d])

The application fix is row 2, `BLOCK_N=64`. The defect under it was root-caused
by the fix author to LLVM machine code:
[raikonenfnu/training#2](https://github.com/raikonenfnu/training/issues/2)
(application) and [#3](https://github.com/raikonenfnu/training/issues/3) (LLVM,
with a checked MIR reproducer). It matters here because it changes what the
workaround means.

gfx1250 encodes only the low eight bits of a VGPR index, so `v1` and `v257` share
an encoded number and the mutable `S_SET_VGPR_MSB` state supplies the high bits.
LLVM keeps a work-item-derived lane offset live in **extended VGPR `v257` across
the whole WMMA body**, then consumes it in a global-address calculation. On this
A0, lane 0 of that value returns an FP32 accumulator-like bit pattern (lanes 1–31
correct), a later integer multiply amplifies it, and the **first final-`DV`
`global_store_b128`** faults. ROCgdb placed the fault there, same displacement
`0x6d0c6e1a` in all four waves. The store is the *observer*, not the producer:
TTIR, TTGIR and LLVM IR all carry the correct address expression; AMDGCN is the
first representation that differs.

Two changes remove it without touching the address formula — rematerialising the
lane offset after the final WMMA, and compiling the same LLVM IR with
`-mattr=-1024-addressable-vgprs`. Both stop the address depending on the old
`v257`.

**This corrects an earlier reading here:** spilling is *not* the cause. The two
tiles do sit in different regimes —

| Tile | LDS | VGPR | Spilled VGPRs | Scratch |
|---|---|---|---|---|
| `BLOCK_N=128` | 32768 | 944, 986, **1024, 1024** | 0, 0, 29, 33 | 0, 0, 84, 92 |
| `BLOCK_N=64` | 16384 | 649, 654, 758 | 0 | 0 |

— but a `waves_per_eu=2` variant with **2372 bytes** of scratch, 5× the spill
traffic, passes 4000 iterations. High pressure *exposes* the victim; it is not
the defect. The coexec schedule likewise increases exposure without being the
whole story: with coexec disabled the full N=128 form still faulted at step 0 in
one run, from the same `v257`.

Validation matrix, from [#3](https://github.com/raikonenfnu/training/issues/3):

| Variant | Result |
|---|---|
| Original N=128, extended VGPRs, seed 4321 | fault at step 0 |
| Identical LLVM IR, `-mattr=-1024-addressable-vgprs` | PASS, 4000 iterations |
| Late lane-offset rematerialisation, clean LLIR replay | PASS, 4000 iterations, twice |
| **N=64 application workaround (row 2)** | **PASS, reduced and full, 4000 iterations** |
| `s_nop 7` after every WMMA | **retracted** — passed once, identical repeat faulted at step 0 |
| NOPs around every `S_SET_VGPR_MSB`, `V_NOP`, `s_wait_alu` drains | fault at step 0 |

Newer LLVM does not resolve it. `85c730242e` adds the gfx1250 pre-RA WMMA
co-execution-window model and Triton `7ff97e3109` pins LLVM `b010a18d`, which
predates it — but rebuilding against post-fix `ce352942` still faults at step 0.
Relevant, insufficient.

The recommended fix is a subtarget-gated backend erratum: stop register
allocation carrying cheap, address-critical work-item values in extended VGPRs
across WMMA regions, rematerialising them after instead.
`-mattr=-1024-addressable-vgprs` is the conservative fallback, at the cost of
heavy spilling. **Native cold-boot B0 validation is owed**, to separate an A0
silicon erratum from a backend requirement for later steppings;
[#2](https://github.com/raikonenfnu/training/issues/2) has the handoff matrix.

### 7.3 Triton language API port ([5])

The **Triton language API** edits that make the HSTU kernels compile on current
upstream `main` (defect [5]). Not workarounds for [1]/[4]/[4c]/[6] — those are
runtime gates, and the kernels already compiled without them.

#### What upstream removed

On every `main` tried, including sglang's `76940ad3` pin, `tl.make_block_ptr`
raises:

```
NotImplementedError: Block pointers have been removed in favor of the tensor
descriptor API
```

`tl.advance` went with them. Upstream's replacement,
`triton.tools.tensor_descriptor.TensorDescriptor`, lowers to NVIDIA Hopper TMA
(`cp.async.bulk.tensor.*`). That path is already in the HSTU attention host
wrapper and is **not** what we turned on: `_should_enable_tma()` returns `False`
on HIP, with an extra guard because gfx950 reports capability `(9, 5)` and would
otherwise pass the Hopper check.

#### What we replaced them with

Masked plain-pointer `tl.load` / `tl.store`. The 2-D sites map one-for-one:

| Before (Triton ≤ 3.8 AMD SDK) | After (this branch; compiles on `main`) |
|---|---|
| `tl.make_block_ptr(base=X, shape=(N, D), strides=(stride_x, 1), offsets=(start_row, 0), block_shape=(BLOCK_N, BLOCK_D), order=(1, 0))` | `rows = start_row + tl.arange(0, BLOCK_N)` and `cols = tl.arange(0, BLOCK_D)` |
| `tl.load(ptr, boundary_check=(0, 1), padding_option="zero")` | `tl.load(X + rows[:, None] * stride_x + cols[None, :], mask=(rows < N)[:, None] & (cols < D)[None, :], other=0.0)` |
| `tl.store(ptr, y, boundary_check=(0, 1))` | `tl.store(Y + rows[:, None] * stride_y + cols[None, :], y, mask=…)` |
| `ptr = tl.advance(ptr, (0, BLOCK_N))` (attention K/V tiles) | rebuild the pointer from the physical sequence offset each tile: `K + offset_kh + (seq_start + load_offs_n)[:, None] * stride_kn + …` — there is no longer a cursor to advance |

`boundary_check` + `padding_option="zero"` is the mask; `other=0.0` is the
padding. Nothing else in the kernels needed a language-level rewrite.

#### Files

26 `tl.make_block_ptr` call sites and 8 `tl.advance` call sites, all gone.
`grep make_block_ptr generative_recommenders` is empty on this branch.

- `ops/triton/triton_hstu_attention.py` — fused/cached HSTU attention forward
  and backward (`_hstu_attn_fwd`, `_hstu_attn_bwd`, and the one-block helpers).
  **Do not feed the remapped `pos_offs_*` into pointer arithmetic.** Those
  coordinates are for the causal / contextual / multi-target *mask* only; V is
  indexed at the physical sequence offset. Mixing them is a silent layout bug,
  not a compile error.
- `ops/triton/triton_layer_norm.py` — `_layer_norm_fwd`,
  `_weighted_layer_norm_fwd`, `_weighted_layer_norm_bwd_dx`,
  `_weighted_rms_norm_fwd`, `_weighted_rms_norm_bwd`.
- `ops/triton/triton_hstu_linear.py` — the fused layer-norm × mul × dropout
  kernels that used 2-D block pointers for X/Y/U.

Jagged concat/split, position embeddings, and addmm were already on plain
pointers (or on the unused Hopper descriptor path) and did not need a port.

#### Compatibility

The same sources still compile and run on AMD 3.6.0 / 3.7.1 / 3.8.0 — masked
`tl.load`/`tl.store` was never removed — so this is a **widening**, not a fork.

`scripts/attn_check.py` is the numeric check that the port matches the old
kernels. All eight deterministic BF16 cases pass forward and backward at the
original `atol=1e-5`, `rtol=0.016`, on both `7ff97e3109` and AMD
`3.8.0+git4cff872c`:

```bash
env -u TRITON_ALLOW_PIPELINING \
  AMDGCN_USE_BUFFER_OPS=0 AMD_SERIALIZE_KERNEL=3 \
  PYTHONPATH=/path/to/triton/python:. \
  python scripts/attn_check.py
```

Those cases are **fixed-shape, single-shot**, which is why they passed throughout
defect [6] and why placing it took so long — what the trainer adds is a different
jagged layout every step. Run it if these kernels are touched, but do not read it
as ruling out the backward.

One **not compile-blocking** tweak: `ops/triton/triton_position.py` uses `&` /
`|` instead of Python `and` / `or` on boolean masks, which Triton now warns on
(and will error on) inside `@triton.jit`.

- **A hang costs a reboot** plus `sudo modprobe amdgpu`, since `amdgpu` is
  blacklisted on the kernel cmdline. A *fault* is recoverable — the process dies
  and the GPU comes back. So leave hang reproducers for last and run **one test
  per process under a hard timeout**: `pytest` orders `unittest` methods
  alphabetically, so a sweep that wedges blames the wrong test.
- **`AMD_SERIALIZE_KERNEL=3` names the faulting kernel**, by making the async
  fault synchronous. Without it you get an address, and a queue wedged behind the
  fault looks exactly like a hang. `AMD_LOG_LEVEL=3` filtered to `ShaderName`
  gives the last dispatch before it.
- **A fault writes a coredump the size of allocated VRAM** (9–36 GB observed).
  `HSA_ENABLE_COREDUMP=0` does *not* suppress it, so keep
  `HSA_COREDUMP_PATTERN` pointed out of the working tree.
- **To time a tile,
  [`scripts/bench_attn_bwd_blockn.py --block-n 64|128`](../../scripts/bench_attn_bwd_blockn.py)**,
  one tile per process so a fault at 128 cannot take the 64 measurement with it.
  It asserts `_hstu_attn_bwd` launched and prints its VGPR count, because the
  easy failure is silently timing the PyTorch path: `hstu_mha` needs
  `kernel=HammerKernel.TRITON`, and the Autotuner's `.cache` holds best-configs,
  not compiled kernels — those are in `fn.device_caches`.
- **Unit tests** need `import fbgemm_gpu` before collection and
  `pip install hypothesis`. In `hstu_attention_test.py`, `test_attn` is a helper
  `pytest` mis-collects, so name the class test explicitly.
- **E2e reproducers** need the yambda-5b cache under `DLRM_DATA_PATH`. The
  batch-1024 production path is
  [`scripts/run_prod_convergence_1gpu.sh`](../../scripts/run_prod_convergence_1gpu.sh)
  ([3.2](#32-run-configuration)); the retired batch-8 path goes
  through [`scripts/run_smoke_shrink_1gpu.sh`](../../scripts/run_smoke_shrink_1gpu.sh),
  which defaults `AMDGCN_USE_BUFFER_OPS=0` and forwards `IMG`,
  `NUM_TRAIN_BATCHES`, `PROGRESS_EVERY`, `AMD_SERIALIZE_KERNEL`,
  `TRITON_ALLOW_PIPELINING` and `DEBUG_NAN_HOOKS`. Check `ps -eo pid,cmd | grep
  train_ranker` first: an interrupted run can outlive its shell, and two

## 9. The node and environment

### 9.1 Hardware and recovery

1× MI450 A0 engineering sample, `gfx1250`, PCI `1002:75c1`, SKU `M4500001`, rev
`0x00` — 256 WGPs, ~432 GiB HBM, **`warp_size=32`** (RDNA, not CDNA wave64).
Software pins are in [3.1](#31-pins) and are not repeated here; note only that
the image's *stock* Triton is 3.6.0, which is why every recipe rebuilds it.

Two facts drive every change here: **one GPU** (the model must fit in one HBM)
and **wave32** (fbgemm's CDNA assumptions are wrong).

`amdgpu` is blacklisted by the kernel cmdline
(`modprobe.blacklist=amdgpu,device_dax,dax_hmem`), so run `sudo modprobe amdgpu`
after every boot — `/dev/kfd` appears ~15 s later.

**Recovery from a hang is a reboot.** The process sticks in uninterruptible `D`
state, `docker kill` returns *"did not receive an exit event"*, MODE2 reset fails
with `error code -62`, `modprobe -r amdgpu` deadlocks. The wedge is whole-device
and survives container teardown: `rocm-smi` still answers while holding VRAM with
no processes alive, and a bare 1024² bf16 matmul in a fresh container never
returns. Untried: `flr`/`bus` reset and the `umr` wave debugger.


**MES wedge: signature, timing, and the power tell (2026-09-17).** Four boots in
one day, each ending in a wedge, gave a consistent picture.

*The first domino is always the same.* In all four boots the first `amdgpu` error
line is

```
amdgpu 0001:01:00.0: MES(0, 0) failed to respond to msg=INVALIDATE_TLBS
```

Everything after it — `REMOVE_QUEUE`, `Failed to evict queue 5`, `ADD_QUEUE`,
`SUSPEND`, `ring buffer is full` — is the driver's *failed recovery*, not the
cause. Counts per boot (failed-to-respond / ring-full): -4 = 71/8, -3 = 71/1,
-2 = 120/642, -1 = 108/38, with `MES might be in unrecoverable state` logged 1-2×
each.

*Wedges happen at startup, not during steady state.* Of seven batch-1024
launches, three died at step 0-1 (two wedges plus one `HW Exception ... reason
:GPU Hang`), and **none** of the four that reached step ≥ 1 wedged later — those
ran 1, 57, 221 and 250 steps. Small n, and the first step is also the longest
single GPU-busy stretch on the card (Triton JIT, first TBE forward, faulting in
~192 GB of tables), so exposure time is a confound rather than a ruled-out
alternative.

*Power, not `GFX%`, distinguishes a wedge from real work.* During the 04:36 wedge
the card reported **GFX 100% while drawing 857 W** — its idle draw on this part —
with VRAM static and no process owning it. A healthy training step reports
GFX ~100% at **~1450 W** with VRAM growing. `GFX%` alone is useless for this
call; check power and the dmesg MES count.

*`gpu_recovery=0` converts every MES wedge into an AC power cycle.* The log reads
`MES might be in unrecoverable state, issue a GPU reset` immediately followed by
`GPU recovery disabled.` — the driver asks for the reset that our mandatory
setting forbids. This is a deliberate trade (state preserved for post-mortem) and
should be re-decided consciously, not inherited.

*`amd-smi reset -G` makes it worse.* On a wedged GPU it hung in `D` state and left
`amd-smi monitor` hanging afterwards. Once `ring buffer is full` keeps climbing
after VRAM has cleared, in-band recovery is exhausted: go straight to AC.

*Ruled out as necessary.* `svm_range_restore_work [amdgpu] hogged CPU` escalated
(7 → 11 occurrences) in the two minutes before the -1 wedge and looked causal,
since SVM migration is exactly what drives TLB invalidation. But boot -4 wedged
with **zero** such messages. Correlated, not necessary.

*Also present, not excluded.* A recurring **corrected** MCE (`CPU:8`, L3/GEN, IO)
fires 2-25× per boot, including 55 s before the -1 wedge. Corrected, so probably
incidental, but it is a real repeating hardware error on this host.

*Mitigations in use.* A persistent `TRITON_CACHE_DIR` on the `/data` mount shrinks
the JIT portion of the first step, which is the bulk of the exposure window;
`NUM_TRAIN_TS=8` cuts the per-window enumeration that dominates startup. Note
that pointing `TRITON_CACHE_DIR` at an *empty* directory makes the first run
slower than baseline, not faster — the benefit starts at run 2.

*Relaunch spacing — and a correction to what this section used to claim.* Until
2026-09-17 this document described `scripts/stop_training.sh` as waiting for VRAM
to drain before returning. **It never did.** The gate parsed `amd-smi monitor`
with `$NF`, and row 2 ends `197.4/432.0 GB`, so `$NF` is the literal string `GB`
and the parsed figure was `0` on every iteration — the loop exited immediately
and every `[stop] VRAM released: 0 GB after 0s` printed during this bring-up was
false. The field is `$(NF-1)`. Fixed, plus a `SETTLE_S=30` wait before the script
returns and `BETWEEN_RUNS_S=30` in `scripts/nan_onset_repeat.sh`.

The reason this matters here: tearing down a ~200 GB address space **is** TLB
invalidation work, and `MES(0,0) failed to respond to msg=INVALIDATE_TLBS` is the
first error in every wedge on this host. `nan_onset_0917i` run 3 was launched
~10 s after the previous trainer was killed and wedged 26 s into its first
forward. **This is a plausible stressor, not a proven cause** — run 1 → run 2 had
the same ~11 s gap and survived, and earlier wedges happened on manual launches
with no preceding teardown at all. The 30 s spacing costs nothing, so it is in
place either way.

*The general lesson, recorded because it cost real time.* The same `$NF` bug had
been found and fixed in `nan_onset_repeat.sh` earlier the same day and was never
grepped for elsewhere, and `after 0s` was read as good news at least six times. **A
guard that reports success instantly and unconditionally is not working.** When
fixing a parsing bug, grep the repo for the pattern rather than fixing the copy
in front of you.

#### Wedge on boot 2026-09-17 05:22 (fifth consecutive INVALIDATE_TLBS first domino)

Fifth wedge in a row whose first `amdgpu` error is the same message. Run
`nan_onset_0917i` run 3 started its first forward at 06:34:35 and wedged at
06:35:01 -- 26 s in, at step 0, having logged no training step.

```
[06:35:01] amdgpu 0001:01:00.0: MES(0, 0) failed to respond to msg=INVALIDATE_TLBS
[06:35:10] amdgpu 0001:01:00.0: MES might be in unrecoverable state, issue a GPU reset
```

`gpu_recovery=0` blocks the reset the firmware asks for, so this escalates to an
AC power cycle. Wedges-at-startup tally is now **4 of 9** b1024 launches dying at
step 0-1; still **0 of 5** that reached step >= 1.

**Unrecoverable confirmed by counter growth with no workload.** After
`scripts/stop_training.sh` reported the trainer gone, `fuser /dev/kfd` empty and
only defunct zombies left, the counters were still climbing:

```
t0    failed-to-respond 43   ring-full 14
t+60s failed-to-respond 58   ring-full 22     (+15/min, +8/min, zero workload)
```

`amd-smi` still answered and read GFX 100% at 861 W with VRAM pinned at
197.4 GB owned by nothing -- the idle-power-at-100%-GFX signature from 9.1. Two
counter samples 60 s apart with no process on the GPU is the practical test for
"unrecoverable" versus "busy": a real workload releases VRAM and stops emitting.

1024. They are kept because the *denominator* analysis below is what matters and
is stack-independent. Config: gin-default depth 3, `MAX_SEQ_LEN=4096`,
`EMBEDDING_ROW_SCALE=0.25`, `BATCH_SIZE=128`, buffer ops off — measured in the
finite region, while the loss was still converging. Step 50 is warmup (1920 ms, carrying compile and autotune).
Steady state is **~322 ms/step, ~395 samples/s, `tflops_real` 35–61, HFU
1.1–1.9%**. HFU tracks `fill` (29–49%) rather than being a fixed number, because
`fill` is the fraction of the dense-equivalent work the jagged batch actually
contains.

**Read `hfu`, not `mfu`.** `num_flops_per_sample` is a *static dense* estimate
(315.7 GFLOP/sample at 3 layers) while jagged attention performs only the `fill`
fraction of it, so `mfu` (3.7–4.2%) describes work that is never executed.
`tflops_real` is the honest count and `hfu` its utilization.

HFU is against **3150 TFLOP/s = 90% of MI450's 3500 TFLOPS dense BF16 matrix
peak**. Two notes on that denominator. `get_gpu_peak_flops` matched nothing and
silently fell back to **MI350X's 2300 TFLOPS**, because these parts report the
generic name `AMD Radeon Graphics` — every earlier perf line in this repo's logs
is normalized against the wrong chip. It is now keyed on `gcnArchName`. And the
silicon peak is deliberate, not the ~75 TFLOP/s this node reaches today:
measured bf16 GEMM is only **1.46× fp32** (67.8 vs 46.5 TF at N=8192), so the
**matrix cores are idle** and everything runs on the vector path at ~1.1 GHz
against a 2.4 GHz max. Normalizing against measured throughput would conflate
model efficiency with BLAS immaturity and shift meaning as kernels improve.

### 10.3 Row 7 follow-up: coexec scheduler root cause

The standalone [`repro_gfx1250_fused_rng.py`](../../scripts/repro_gfx1250_fused_rng.py)
reproduces row 7 directly at the recorded `N=18187`, `D=512`, bf16 launch.  It
also checks the gradients, recomputed output, and all three dropout masks, which
exposed silent corruption at four warps in addition to the two-warp fault.

The proximate compiler root cause is the gfx1250 **coexec machine schedule under
LLVM expert-scheduling mode**, enabled by ROCm/triton commit
[`89db5e470c`](https://github.com/ROCm/triton/commit/89db5e470c330ea6f51ea3763a5dda58083f780c).
That commit is an ancestor of `4cff872c`, but is absent from the passing AMD
3.7.1 commit `0263a6a6`.  Holding the source, LLVM, input, two-warp launch, and
all other options fixed gives this matrix:

| coexec attribute | expert mode | result | backward VGPRs |
|---|---|---|---:|
| on | on | memory-aperture fault | 254 |
| off | on | correct | 135 |
| on | off | correct | 254 |

The last two rows separate the scheduler defect from register pressure alone.
With both controls enabled, two warps fault and four warps silently corrupt
results; eight warps is correct because Triton does not request coexec above
four warps.  Disabling coexec fixes the two- and four-warp kernels, including
`FAST_DROPOUT=True` and `COMPUTE_Y=False`.

For an unmodified `3.8.0+git4cff872c`, the immediately available compiler
workaround is:

```bash
AMDGCN_USE_BUFFER_OPS=0 TRITON_HIP_USE_EXPERT_SCHEDULING=0 \
  python scripts/repro_gfx1250_fused_rng.py
```

A narrower compiler workaround is to backport ROCm/triton
[`#11272`](https://github.com/ROCm/triton/pull/11272), then run with
`TRITON_HIP_USE_COEXEC_SCHEDULER=0`.  The backport adds a cache-invalidating
knob so toggling the scheduler cannot reuse an incompatible cached binary.  The
existing separated-RNG application workaround remains preferable when only
this operation needs protection; `num_warps=8` is another verified but
performance-untuned kernel workaround.  The recommended image already contains
the proposed ROCm 7.14 / torch 2.11 gfx1250 nightly stack, so reinstalling those
wheels does not address this compiler-scheduling defect.

**Latest-main retest (2026-09-03): fixed.** Upstream `triton-lang/triton` main
at [`7ff97e3109`](https://github.com/triton-lang/triton/commit/7ff97e310935b4a79794878dbc911f9af25d38d9),
built from source with bundled LLVM `b010a18d`, passes the original two-warp
launch and the four-warp and `FAST_DROPOUT=True` corruption cases with default
settings.  The generated LLIR still carries
`"amdgpu-sched-strategy"="coexec"`, expert scheduling is still enabled, and the
two-warp kernel reports 260 VGPRs.  Therefore the row-7 defect does **not**
persist in that current compiler stack; it was fixed by intervening
Triton/LLVM codegen changes rather than by disabling coexec.  The precise
fixing commit has not been bisected.

## 11. Retracted

**`and`/`or` on tensors is not a bug** and the `triton_position.py` rewrite was
cosmetic. Triton warns, but `code_generator.py:visit_BoolOp` (3.6.0) lowers them
to `logical_and`/`logical_or`, which for boolean masks is exactly `&`/`|`.
Nothing goes unmasked; the position test passing afterwards was nondeterminism.

**Register spilling is not what causes defect [6]**, and this document said it
was. The `BLOCK_N=128` tile does reach the 1024-VGPR ceiling and spill while
`BLOCK_N=64` does not, but the causal chain runs through an extended VGPR held
across the WMMA region — a `waves_per_eu=2` variant with 5× the scratch passes
4000 iterations. See [Root cause of the attention-backward
fault](#72-root-cause-of-the-attention-backward-fault-6--4d).

**`s_nop 7` after every WMMA is not a fix** for it either (retracted upstream):
it passed 4000 iterations once and an identical repeat faulted at step 0. The
durable controls are late lane-offset rematerialisation and disabling
1024-addressable VGPRs.

**The uninitialized-output hypothesis for [3] is refuted**, and it was a
batch-128 hypothesis. `concat_2D_jagged` / `split_2D_jagged` allocate outputs
with `torch.empty` and size their launch grid from `max_seq_len` while masking
stores on `offs_n < seq_len_a + seq_len_b` from the offsets, with nothing tying
the two together. An audit of all 7 reachable call sites found the coverage
condition violated by **0 rows everywhere**; `max_seq_len` always comes from
`fx_infer_max_len()` (`common.py:483-493`) applied to the same length tensors
the offsets are cumsum'd from, so it cannot drift below its own offsets. The
decisive point: the condition
`len_a(z) + len_b(z) <= ceil(max_seq_len/BLOCK_N)*BLOCK_N` is **per-element and
contains no `B` term at all**, so it cannot produce a defect that fires 3-in-4
at batch 128 and 0-in-3 at batch 8. Two scripts outlive it with general value:
[`repro_jagged_concat_uninit.py`](../../scripts/repro_jagged_concat_uninit.py)
as a regression test for the invariant, and
[`nan_poison_hook.py`](../../scripts/nan_poison_hook.py) as an uninitialized-read
detector. (Was `docs/batch128_nan_uninit.md`, folded in and deleted 2026-09-17.)

**`hstu_compute::test_compute_output` was an inherited code bug, not a GPU bug**:
the forward dropped `mul_u_activation_type`, applying no activation while its own
backward applied one. A one-line fix takes that parameter grid from 32 mismatches
to 0. Our file is byte-identical to `mlcommons/training@master`, and it is dormant
in the benchmark, which only passes `"none"`.

# Bring-up on MI450 B0, host `heliosr-1b112-a30-4` (gfx1250, single GPU)

The same yambda-5b HSTU ranker, the same branch, the same container image and the
same pins that train end to end at batch 1024 on a0
([`mi450_a0.md`](../mi450_a0/mi450_a0.md)) **do not run here**. The batch-1024
run dies at **step 212** with a GPU page fault, preceded by fbgemm
`EmbeddingBoundsCheck` warnings carrying indices the dataset provably cannot
emit.

**This is not a software regression and not a data problem.** The root cause
reproduces in **eleven lines of `torch` with no dataset, no fbgemm and no
Triton**: *scattered GPU gathers on this host silently return wrong data*. A
gather from a table whose row `i` is filled with the value `i` comes back with
rows that do not contain `i` — no fault, no warning, no error code. Three
independently written gather kernels all corrupt; a matmul stress loop over the
same period corrupts **zero** times.

**Status: blocked.** There is no workaround. Every environment knob, allocator
setting and serialization mode tested leaves the corruption in place — it only
changes the rate. The one open question is *hardware vs. compiler backend*, and
[§6](#6-the-one-open-question) gives the single experiment that settles it.

Host, silicon and driver identity are in [§1](#1-host-identity). Throughout
these docs this host is **b0** and the host of
[`mi450_a0.md`](../mi450_a0/mi450_a0.md) is **a0**; that is the naming
convention, independent of what the parts report about themselves.

  ([§4](#4-the-reproducer)).

One caveat stated for completeness: the `:gfx1250` image here is a **local build**
of [`Dockerfile.amdprimus0815`](../../Dockerfile.amdprimus0815), not a pulled

Triton, ROCm and Python versions all match a0's recorded pins.

## 2. The e2e symptom

a0's batch-1024 recipe ([`mi450_a0.md` §2.3](../mi450_a0/mi450_a0.md#23-build-and-run)),
run unmodified here:

```
step=212
EmbeddingBoundsCheck (VBE false): (at least one) Out of bounds access for
  batch: 214, table: 1, bag element: 5, idx: -9223372034707292161,
  num_rows: 2347656, indices_start: 11142, indices_end: 11151,
  T: 14, B: 1024, b_t: 1238. Setting idx to zero.
  ... (many, growing)
Memory access fault by GPU node-2 (Agent handle: 0x48aad210) on address
  0x7bdfc9374000. Reason: Page not present or supervisor privilege.
Traceback (most recent call last):
```

and in `dmesg`:

```
amdgpu 0001:01:00.0: [gfxhub0] no-retry page fault (src_id:0 ring:24 vmid:3 pasid:33)
amdgpu 0001:01:00.0:   in page starting at address 0x000253dfc9381000 from IH client 27 (GC_UTCL2)
amdgpu 0001:01:00.0:   cookie node_id 4 fault from die AID0.XCD2
amdgpu 0001:01:00.0: GCVM_L2_PROTECTION_FAULT_STATUS_LO32:0x00C04061
amdgpu 0001:01:00.0: 	 Faulty UTCL2 client ID: TCP (0x8)
amdgpu 0001:01:00.0: 	 MORE_FAULTS: 0x1
amdgpu 0001:01:00.0: 	 PERMISSION_FAULTS: 0x3
```

Two details in that output are the whole story.

**The out-of-bounds indices are impossible.** The bad values observed are
`389387`, `522440`, `579272` and `639688` against `num_rows: 323348`, plus
`-9223372034707292161` (`0x8000_0001_xxxx_xxxx`) against `num_rows: 2347656`.
The dataset **cannot produce any of them**: every id is wrapped with `% num_rows`
against a positive modulus read from the same `yambda_5b_table_rows()` the table
sizing reads, so out-of-range is arithmetically impossible, and there is no
negative sampler or candidate generator anywhere in `dlrm_v4/`
([§3](#3-sanity-checks-that-pass)). A value of `389387` when the table has
`323348` rows, and an int64 with the sign bit set, did not come from the input
pipeline. **They were corrupted in flight, on the GPU.**

**The faulting client is `TCP`** — the vector-memory path's L2 translation
client, not a shader-export or SDMA client. That is the unit that services
exactly the scattered per-lane addresses a gather issues.

Recovery from the wedge is a reboot, as on a0.

## 3. Sanity checks that pass

These were run first, and they are the reason the investigation moved to the
hardware rather than to the model or the data.

| Check | Result |
|---|---|
| Dataset ↔ shrunk-table consistency (`EMBEDDING_ROW_SCALE=0.25`) | **Consistent.** Table sizing and id wrapping both call `yambda_5b_table_rows()`; wrap is `%` with a positive modulus; no negative-id source exists in `dlrm_v4/` (only `item_to_artist`/`item_to_album`, both wrapped). 400 samples scanned: all 14 features in range |
| Dataset integrity | All 16 cache files + 2 mappings + popularity table checksum OK |
| GPU present, enumerated, healthy idle | `rocm-smi` clean, ~432 GiB HBM visible, no RAS errors |
| Basic GPU functionality — small matmuls, elementwise, reductions, D2H/H2D | **Pass** |
| **Matmul stress, 188,179 iterations** | **0 mismatches** |
| Co-tenancy excluded — reproducer re-run with GPU provably idle (`rocm-smi`: *No KFD PIDs currently running*, 0 % util) | **Rates unchanged** ([§4.2](#42-the-idle-gpu-control-and-what-it-excludes)) |
| Batch-8 smoke recipe | Runs (this is the a0 e2e reproducer for defect [6], unrelated) |
| `HSTU_HAMMER_KERNEL=PYTORCH` arm | Names the faulting kernel: `at::native::vectorized_gather_kernel<16, long>` |

The matmul result is the control that matters: **188,179 iterations of dense
compute over the same wall-clock window produced zero wrong answers, while
gathers interleaved with them produced 3,129 (1.66 %).** Whatever is broken is
specific to scattered addressing, not to the compute units, the HBM at large, or
thermals.

## 4. The reproducer

**What this section is for.** [§2](#2-the-e2e-symptom) leaves an accusation
without a suspect: indices appear that the pipeline cannot have produced, and the
GPU faults. The obvious readings are that the model is wrong, the data is wrong,
or some kernel deep in a 14-table HSTU ranker is wrong — and none of those can be
disentangled inside a run that involves the dataset, fbgemm, TorchRec sharding,
dozens of Triton kernels and ~150 GiB of live tensors at once. **This section
collapses that to the smallest thing that still fails.** Its job is to establish
three claims, each of which is what makes the [§5](#5-how-it-explains-the-e2e-blocker)
argument and the [§6](#6-the-one-open-question) escalation possible at all:

1. **The failure is corruption, not a crash.** Everything in [§2](#2-the-e2e-symptom)
   is *downstream* evidence — a fault is what you see after something has already
   gone wrong. This section catches the moment data becomes wrong, while the
   process is still healthy and no error has been raised anywhere.
2. **Nothing in this repo is involved.** No dataset, no fbgemm, no model, no
   HSTU kernel, no TorchRec. If ~70 lines of stock `torch` on random integers
   corrupt, then no amount of work on the benchmark can fix it, and a0's
   recipe was never going to reproduce here.
3. **It is not one buggy kernel.** The arms are chosen so that the *only* thing
   they share is the layer beneath them — which is what
   [§4.1](#41-reading-the-layer-column-who-owns-this) turns into an owner.

**How it works.** [`scripts/repro_gfx1250_gather_corruption.py`](../../scripts/repro_gfx1250_gather_corruption.py)
— torch only, optional Triton, **no dataset, no fbgemm**. It builds an `N × D`
table with row `i` filled with the value `i`, gathers 16,384 random rows, and
checks `out[:, 0] == idx`. **The table is its own answer key**: the correct
output is known in advance, exactly, for every index, with no tolerance and no
reference implementation to disagree with. Any mismatch is silent corruption by
construction — there is no third possibility. `N = 2,347,656` is the shrunk
yambda item-table row count, so the address footprint is the workload's, not an
arbitrary one.

**Why it is run as several arms.** A single failing kernel proves nothing about
where the defect lives — it would just be a bug in that kernel. Each arm gathers
*the same data with the same indices* through a **different implementation**, and
the arms are deliberately drawn from **different layers of the stack** (the
`Layer / owning component` column): two are upstream PyTorch kernels compiled by
hipcc, one is a kernel written from scratch for this test and compiled by Triton,
which never touches PyTorch's kernel library. **Agreement across implementations
that share no source code is the evidence**. The `D` sweep then varies the row
width while holding the implementation fixed — which turned out to matter far
more than expected ([§4.3](#43-the-64-byte-row-signature-and-a-retraction)).

```
python3 scripts/repro_gfx1250_gather_corruption.py
```

**On this host, 600 trials per arm.** Every figure below was reproduced on a
**provably idle GPU** (`rocm-smi`: *No KFD PIDs currently running*, 0 % util at
launch) — see [§4.2](#42-the-idle-gpu-control-and-what-it-excludes):

An earlier, co-tenanted run of the same script gave rates within noise of these
(`index_select` D=16 13.33 %, `gather` D=16 19.67 %, `triton` D=16 56.50 %,
`gather` D=4 1.17 %, `triton` D=4 28.33 %).

**Expected on a healthy host: `0 / 600` on every line.**

Three separately authored kernels — two of them upstream ATen, one written from
scratch for this test — corrupt. The Triton kernel was verified correct against a
fresh allocation (`0 / 600` at `D = 16` before the allocator churn), so its 56 %
is corruption, not a logic bug.

### 4.1 Reading the layer column: who owns this

The two ATen arms and the Triton arm **diverge above the compiler and converge at
it**. `torch.index_select` and `torch.gather` are HIP C++ in PyTorch's kernel library, built
by hipcc; the Triton arm never touches that library — it is generated by Triton's
own AMD backend from a kernel written for this test. Above LLVM they share no
code. From the LLVM AMDGPU backend downwards — backend, ROCr/HSA runtime, KFD
driver, firmware, silicon — they share everything.

**All three corrupt. So the component at fault is at or below the LLVM AMDGPU
backend, and follow-up with the PyTorch-ROCm or Triton teams is misdirected.**
The candidate owners, in the order [§6](#6-the-one-open-question) would settle
between them:

| Layer | Shared by all three arms? | Follow up with | Implicated? |
|---|---|---|---|
| PyTorch ATen ROCm kernels | no — Triton arm bypasses it | PyTorch-ROCm | **No** — Triton arm fails without it |
| Triton AMD backend | no — ATen arms bypass it | Triton / AMD Triton | **No** — ATen arms fail without it |
| **LLVM AMDGPU backend** (address lowering, memory model) | **yes** | **ROCm compiler team** | **Candidate** |
| **ROCr / HSA runtime, KFD driver, firmware** | **yes** | **ROCm runtime / KFD, firmware** | **Candidate** |
| **Silicon** (`TCP` / `UTCL2` translation path) | **yes** | **hardware / board** | **Candidate** — see [§1](#1-host-identity) |

**hipBLASLt and rocBLAS are explicitly not implicated.** No arm here is a GEMM,
and the 188,179-iteration matmul control in [§3](#3-sanity-checks-that-pass) —
which *is* the hipBLASLt/rocBLAS path — returned **zero** wrong answers over the
same window. Do not route this to the BLAS teams.

Distinguishing the three remaining candidates from each other is exactly what
[§6](#6-the-one-open-question) is for, and it needs the a0 run: a clean a0 puts
it in silicon or firmware, a dirty a0 puts it in the backend or runtime.

### 4.2 The idle-GPU control, and what it excludes

This host is **shared — 44 user accounts, one GPU** — and most co-tenant work on
it is GEMM and kernel-perf benchmarking (`op-evolve-grouped-gemm-*`,
`aiter_gemm`, `mxfp8-gemm`, `megamoe`, `flux`). That raises two separate
questions, and they have different answers.

**"Other people test fine here" is consistent with this defect, not evidence
against it.** A dense GEMM is the one access pattern with a clean control:
188,179 matmul iterations, **zero** mismatches ([§3](#3-sanity-checks-that-pass)),
over the same window in which gathers failed 3,129 times. A GEMM tile walks a
small, blocked, highly local working set. Beyond that, perf benchmarking
measures TFLOP/s, and where it checks numerics it uses tolerance-based `allclose`
on small dense tiles — **a 1-in-100 silently wrong gather would not register in
any of it.**

**But co-tenancy was also a candidate *cause*, and it is now excluded.**
Concurrent processes mean multiple VMIDs contending on the very unit the driver
names as faulting (`UTCL2`, client `TCP`), and a translation-invalidation bug
across contexts would explain why serializing *our* dispatches
([§4.5](#45-what-does-not-fix-it)) changes nothing. Every earlier measurement had
unknown co-tenants. **Re-run with the GPU provably idle — `rocm-smi` reporting
*No KFD PIDs currently running* and 0 % utilisation at launch — the rates are
unchanged.** Multi-tenancy is not the mechanism, and a quiet box is not a
workaround.

> Caveat: "idle at launch" is not "idle throughout" on a box with this many
> users. The control should be repeated before anything load-bearing rests on it.

### 4.3 The 64-byte row signature, and a retraction

The idle-GPU run swept `D` for `index_select`, and the result is much narrower
than "scattered gathers corrupt":

**`index_select` fails at `D = 16` and nowhere else** — clean at 4, 64, 128, 256
and 512. And `D = 16` is the worst case for *every* arm tested there:
`gather` is 16× worse at 16 than at 4, `triton` ~1.7× worse.

**This retracts part of the earlier analysis in this document.** A previous
revision explained the `D = 4` rates as a footprint effect — a smaller table
touching fewer distinct pages. **That explanation is wrong and the data refutes
it:** at `D = 512` the table is ~4.8 GiB, 32× the footprint of `D = 16`, and it
is perfectly clean. Corruption does not rise with table size.

What survives, and what does not:

- **Still valid:** [§4.6](#46-address-spread-not-address-region)'s experiment,
  which holds kernel *and* `D` fixed and varies only the index range. Spread
  within a fixed configuration does drive the rate.
- **Retracted:** any reading of the `D` sweep as a footprint or spread effect.
  Across `D`, corruption tracks **something about the generated access pattern**,
  not the amount of memory touched.

`D = 16` float32 is a **64-byte row**. That is the one strong hypothesis on
offer — a row granularity interacting badly with cache-line or `TCP` request
granularity — and it is **speculation**, offered because it is testable, not
because it is established. What matters for a bug report is the observation
itself: **a sharp, reproducible, configuration-specific signature at 64-byte
rows, across three independently written kernels.** That is far more actionable
than "gathers are unreliable", and it is the first thing to hand whoever picks
this up.

It also sharpens [§6](#6-the-one-open-question) rather than settling it. A razor-
sharp dependence on one access shape is not what generic marginal silicon looks
like; but the Triton arm's kernel is trivially simple and corrupts at 31–54 %,
which is not what a compiler miscompilation of one vectorisation config looks
like either. **Both candidates survive. The a0 run is still the discriminator.**

### 4.4 What the corruption looks like

- Corrupted rows contain **garbage** (e.g. `2.3694278276172396e-38`), not
  mis-selected rows from the source — so it is not an index arithmetic error.
- The **source table stays intact**: re-reading it afterwards is clean.
- **Replaying the same `idx` gives the correct answer.** The failure is
  transient, not a bad row or bad HBM page.
- The CPU reference for the same inputs is always correct.

### 4.5 What does not fix it

| Knob | Rate |
|---|---|
| baseline | 12.00 % |
| `torch.cuda.synchronize()` after every gather | unchanged |
| allocator variants (incl. `expandable_segments`) | 12.00 % / 6.67 % / 3.00 % |
| `AMD_SERIALIZE_KERNEL=3` | 3.83 % |
| `GPU_MAX_HW_QUEUES=1` | 9.83 % |
| `HSA_ENABLE_SDMA=0` | 17.17 % |
| `HSA_XNACK=0` | 10.00 % |
| `HSA_XNACK=1` | 9.50 % |

`AMD_SERIALIZE_KERNEL=3` reducing but **not eliminating** the rate is the load-bearing
observation: with one kernel in flight at a time the corruption persists, so the
fault occurs **within a single dispatch**, not from a race between dispatches or
between a kernel and a copy.

### 4.6 Address spread, not address region

Varying only the range the random indices are drawn from, at fixed iteration
count:

| Index distribution | Rate |
|---|---|
| full table | 12.0 % |
| any single 1/8 slice of the table | 0.3 – 3.0 % |
| one row, repeated | **0.0 %** |

Every eighth of the table is individually near-clean, but drawing across all of
them is 4–40× worse, and a single hot row never fails. **The rate tracks address
*spread*, not any particular region of memory.** That is the signature of
address-translation pressure — many distinct pages touched per wavefront — and it
lines up exactly with the driver naming `UTCL2` client `TCP` as the faulting
unit in [§2](#2-the-e2e-symptom). It also rules out a bad HBM region, which would
show up as one dirty slice rather than as a spread effect.

## 5. How it explains the e2e blocker

The chain from [§4](#4-the-reproducer) to [§2](#2-the-e2e-symptom) is direct, and
every link is observed rather than assumed:

1. **The model is one enormous scattered gather.** An embedding-bag lookup *is*
   a gather: 14 tables, batch 1024, thousands of jagged events per sample, every
   lane pulling a different row from a multi-gigabyte table. This is the widest
   address spread in the whole workload — precisely the condition
   [§4.6](#46-address-spread-not-address-region) shows is worst.
2. **Some fraction of those gathers returns garbage.** At the measured
   1–20 % *per-trial* rate on a 16,384-row gather, a run doing thousands of much
   larger gathers per step will hit corruption within a few hundred steps. It
   died at step 212.
3. **Garbage flows into things used as indices and pointers.** Corrupted
   embedding output feeds subsequent indexing; corrupted index tensors are read
   back by fbgemm — which is why `EmbeddingBoundsCheck` reports `389387` against
   `323348` rows, and an int64 with the sign bit set. `EmbeddingBoundsCheck`
   clamps what it catches ("Setting idx to zero"), so the run limps on while the
   corruption keeps arriving.
4. **A corrupted pointer eventually escapes the bounds check** — inside a Triton
   kernel, or in an address computed rather than looked up — and dereferences a
   non-canonical address. That is the `no-retry page fault`, `UTCL2` client
   `TCP`, and the `HSA_STATUS_ERROR_EXCEPTION`.

The wandering onset is consistent with this too: which step dies depends on when
a corrupted value first lands somewhere that is *used as an address* rather than
merely as a number, which is an allocator-and-schedule accident, not a
deterministic step.

**This is why a0's recipe cannot be reproduced here, and why chasing it at the
Triton level is wasted effort.** a0's six Triton/LLVM defects and
the [3] int32 fix are all present and correct on this branch — they are not the
problem here. The failure is one layer below all of them.

**Corollary worth stating:** the failure mode is *silent wrong data first,
crash second*. A run on this host that does **not** crash is not therefore a good
run. Any number produced here — loss, AUC, throughput — is untrustworthy until
[§4](#4-the-reproducer) reads `0 / 600`.

## 6. The one open question

**Faulty silicon on this host, or a defect in the shared LLVM AMDGPU backend?**

The three-kernel agreement in [§4](#4-the-reproducer) is strong but **not a fully
independent triple**: HIP (which compiles the ATen kernels) and Triton both lower
through the same LLVM AMDGPU backend. A memory-model or address-lowering bug
there could corrupt all three arms on any gfx1250. So the reproducer alone does
not distinguish hardware from compiler.

**The decisive experiment is one command on a0:**

```
python3 scripts/repro_gfx1250_gather_corruption.py
```

| Outcome on a0 | Conclusion |
|---|---|
| `0 / 600` everywhere | **b0's GPU is faulty.** Same software, same readable device identity as a0, opposite result. Escalate as a hardware/board issue, and get the two boards' firmware and stepping compared out of band — [§1](#1-host-identity) shows neither is readable from the hosts |
| non-zero anywhere | **Stack-wide gfx1250 defect**, and **[`mi450_a0.md` §3.1](../mi450_a0/mi450_a0.md#31-the-confirming-runs)'s batch-1024 `train_loss=0.13826` needs re-examination** — it may have been produced over silently corrupted gathers that happened not to crash |

This has not yet been run on a0. Until it is, neither branch should be asserted.

Secondary, if a0 comes back clean: the kernel cmdline differs between the hosts
(`iommu=pt pci=realloc=off` here). `iommu=pt` is a plausible interaction with a
translation-path fault and is cheap to vary — but it is a *secondary* line of
enquiry, because the corruption is present with `HSA_XNACK` both on and off and
within a single serialized dispatch, which is hard to reconcile with a host-IOMMU
cause.

## 7. Ruled out

Each of these was tested, not assumed:

| Hypothesis | Why it is out |
|---|---|
| Wrong Triton version / missing a0 fixes | Correct commit `7ff97e3109`; the [3] int32 fix and all six workarounds present. The reproducer needs no Triton at all |
| Defect [6] / `BLOCK_N` / pipeliner | Reproducer contains no HSTU kernel |
| Bad input data | [§3](#3-sanity-checks-that-pass) — checksums, range scan, structural proof that out-of-range ids cannot be emitted |
| Table-shrink / dataset-wrap mismatch | Sizing and wrapping read the same function; verified empirically |
| Plain int32 / 2³¹ offset overflow | Reproducer's largest tensor is far below 2³¹ elements at `D = 4`, and `D = 4` still fails |
| Stale or wrong container image | Reproduced on `amdprimus/amdprimus:gfx1250-20260910` as well |
| Dead card, bad HBM, thermal throttling | 188,179 matmuls clean; single-row gather 0 %; corruption tracks spread, not region ([§4.6](#46-address-spread-not-address-region)) |
| Race between dispatches, or with SDMA | `AMD_SERIALIZE_KERNEL=3` and `HSA_ENABLE_SDMA=0` both leave it in place |
| PyTorch caching-allocator bug | Present under every allocator configuration, and in Triton kernels writing into fresh `torch.empty` buffers |
| **Interference from other tenants** (44 accounts share this GPU) | Rates are unchanged with the GPU **provably idle**, no KFD PIDs ([§4.2](#42-the-idle-gpu-control-and-what-it-excludes)) |
| **"Other users' tests pass, so the GPU is fine"** | Co-tenant work here is GEMM/perf benchmarking — the one pattern with a clean control (188,179 matmuls, 0 mismatches) — and it measures TFLOP/s, not exact correctness. It would not detect this ([§4.2](#42-the-idle-gpu-control-and-what-it-excludes)) |
| Table size / memory footprint | `index_select` is **clean at `D = 512`** (~4.8 GiB table) and fails only at `D = 16` (~150 MiB) ([§4.3](#43-the-64-byte-row-signature-and-a-retraction)) |
| Driver / kernel drift vs a0 | Same kernel `6.14.0-37-generic`, same DKMS 7.1.1 |
| "It's just B0 vs A0 silicon" | **Not usable as an explanation from here** — b0 and a0 are indistinguishable through PCI and VBIOS (both rev `0x00`, SKU `M4500001`), so any stepping difference has to be established out of band ([§1](#1-host-identity)) |

# Bring-up on MI450 A0 (gfx1250, single GPU)

Running the yambda-5b HSTU ranker on an **MI450 A0 engineering sample**, one GPU.
As of **2026-09-04 the benchmark trains end to end on Triton kernels**: 4000
batches, `run_stop`, finite loss, an eval AUC. Getting there took workarounds for
six distinct Triton/LLVM defects ([1], [2], [4], [4c], [5], [6]), plus three
fbgemm patches for wave32 and a table shrink to fit one GPU. **None of it is in
the benchmark's math.**

This document leads with the stack that works and the changes it depends on. The
per-version defect history — what breaks on 3.6.0, AMD 3.7.1 and AMD 3.8.0 — is
kept for reference in [Historical: defects by Triton
version](#historical-defects-by-triton-version), because it is no longer the
recommended path.

**Two caveats before the recipe.** A completed 4000-batch run is not a converged
one, and the `nan` defect [3] is **not** cleared by it — the run is ~9× too short
in samples to reach where `nan` has appeared before. And the remaining
attention-backward defect [6] is *worked around, not fixed*: the LLVM-level
hazard is still there, tracked in
[raikonenfnu/training#3](https://github.com/raikonenfnu/training/issues/3). See
[What the run does not establish](#what-the-run-does-not-establish).

Branch `chcai/mi450_a0`. Companion to [`training_recipe.md`](./training_recipe.md)
and [`perf_opt.md`](./perf_opt.md).

### Build and run

[`scripts/build_triton_from_source.sh`](../scripts/build_triton_from_source.sh)
`pip install -e`s Triton into `/opt/triton-custom` **inside a container**; it does
not produce an image. So the sequence is: start a long-lived container, build
Triton in it, then train in it.

```bash
# 1. Long-lived container from the :gfx1250 image, repo and yambda cache mounted.
docker run -d --name triton-7ff97e --entrypoint sleep \
  --device=/dev/kfd --device=/dev/dri \
  --group-add "$(getent group video | cut -d: -f3)" \
  --group-add "$(getent group render | cut -d: -f3)" \
  --ipc=host --security-opt seccomp=unconfined --shm-size=64g \
  -v "$PWD:/workspace/recommendation" \
  -v "${DLRM_DATA_PATH:-$HOME/dlrm_data}:/data/mlperf_dlrm_v4" \
  -e PYTHONPATH=/workspace/recommendation -e DLRM_DATA_PATH=/data/mlperf_dlrm_v4 \
  recommendation-amdprimus0815:gfx1250 infinity

# 2. Build Triton main in it (~5 min on this node).
docker exec -w /workspace/recommendation triton-7ff97e \
  env TRITON_COMMIT=7ff97e310935b4a79794878dbc911f9af25d38d9 \
  ./scripts/build_triton_from_source.sh

# 3. Train: 4000 batches, one GPU, shrunk tables. These are the
#    run_smoke_shrink_1gpu.sh defaults, passed explicitly because the trainer is
#    invoked directly rather than through the runner's own `docker run`.
docker exec -w /workspace/recommendation \
  -e AMDGCN_USE_BUFFER_OPS=0 -e HSTU_HAMMER_KERNEL=TRITON \
  -e PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True \
  -e HSA_ENABLE_COREDUMP=0 -e HSA_COREDUMP_PATTERN=/tmp/gpucore.%p.gpu \
  -e EMBEDDING_ROW_SCALE=0.25 -e HBM_CAP_GB=400 \
  -e BATCH_SIZE=8 -e NUM_WORKERS=2 -e PREFETCH_FACTOR=2 \
  -e HISTORY_LENGTH=4086 -e MIN_HISTORY=64 -e MAX_SEQ_LEN=4096 -e HSTU_NUM_LAYERS=3 \
  -e START_TS=150 -e NUM_TRAIN_TS=1 \
  -e NUM_TRAIN_BATCHES=4000 -e NUM_EVAL_BATCHES=20 \
  -e EVAL_EVERY_N_WINDOWS=1 -e EVAL_EVERY_DATA_PCT=0 -e AUC_THRESHOLD=1.0 \
  -e GPUS_PER_NODE=1 -e NNODES=1 -e NODE_RANK=0 -e WORLD_SIZE=1 \
  -e MASTER_ADDR=localhost -e MASTER_PORT=29501 -e NCCL_SOCKET_IFNAME=lo \
  -e PROGRESS_EVERY=100 \
  triton-7ff97e python -m generative_recommenders.dlrm_v4.train.train_ranker \
    --dataset yambda-5b --mode streaming-train-eval
```

`docker commit triton-7ff97e <tag>` and then
`IMG=<tag> NUM_TRAIN_BATCHES=4000 ./scripts/run_smoke_shrink_1gpu.sh` is the same
run through the runner, which is where those defaults come from — at the cost of
a ~47 GB image layer.

`AMDGCN_USE_BUFFER_OPS=0` is the only correctness flag that has to be passed —
and the runner already defaults it. Every other workaround in the fix set is
gated in code on arch and Triton version, so it applies itself. The runner also
defaults `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` (either setting
works; it was ruled out as a cause of [6]) and `HSTU_HAMMER_KERNEL=TRITON`.
`AMD_SERIALIZE_KERNEL=3` is optional here — the run passes with and without it —
and costs throughput, so leave it off outside debugging.

**Start from an idle GPU.** A faulted rank stays wedged and its dataloader
workers are orphaned, both holding HBM, so a following run starts under
artificial memory pressure. `scripts/bisect_hooks/gpu_cleanup.sh` clears them;
check `rocm-smi --showmemuse` reads 0 % first.

~125–150 before the fix.

### What the run does not establish

- **It does not clear [3], the `nan`.** 4000 × batch 8 is 32,000 samples. On AMD
  3.7.1 the `nan` first appeared at step 2200 of a **batch-128** run — 281,600
  samples, ~9× further in. A batch-128 run of ≥3000 steps is what would compare,
  and that has not been run on this stack.
- **The AUC is not a quality signal.** `0.5233` after 32,000 samples is barely
  above chance; it says the eval path runs and produces a finite metric.
- **The model is shrunk.** `EMBEDDING_ROW_SCALE=0.25` (~140 GB of tables) against
  a ~559 GiB fp32 reference, with ids modulo-wrapped into the smaller vocabulary.
  This is not a valid MLPerf configuration.
- **One GPU only.** Nothing here exercises sharding across ranks, and one
  workaround (row 2) touches device-0 initialisation at import time, which is
  exactly where a multi-rank run would notice.
- **The buffer-op hang class is avoided, not fixed.** `AMDGCN_USE_BUFFER_OPS=0`
  is load-bearing, and [1b] shows hangs that survive it.
- **Performance is unmeasured on this stack.** Two workarounds (rows 2 and 3)
  trade throughput for correctness and neither cost has been quantified.

### Root cause of the attention-backward fault ([6] / [4d])

The application-level fix is row 2, `BLOCK_N=64`. The defect underneath it was
root-caused by the fix author down to LLVM machine code and is tracked in
[raikonenfnu/training#2](https://github.com/raikonenfnu/training/issues/2)
(application) and
[#3](https://github.com/raikonenfnu/training/issues/3) (LLVM, with a checked MIR
reproducer). Summarising, because it changes what the workaround means:

gfx1250 encodes only the low eight bits of a VGPR index, so `v1` and `v257` share
an encoded number and the mutable `S_SET_VGPR_MSB` state supplies the high bits.
LLVM keeps a work-item-derived lane offset live in **extended VGPR `v257` across
the whole WMMA body**, through hundreds of mode transitions, then consumes it in
a global-address calculation. On this A0, lane 0 of that value comes back as an
FP32 accumulator-like bit pattern (lanes 1–31 are correct), a later integer
multiply amplifies it, and the **first final-`DV` `global_store_b128`** faults on
an arbitrary address. ROCgdb placed the fault there, with the identical
displacement `0x6d0c6e1a` in all four waves. The store is the *observer*, not the
producer: TTIR, TTGIR and LLVM IR all carry the correct address expression, and
AMDGCN is the first representation that differs.

Two independent changes remove it, neither of which alters the address formula —
rematerialising the lane offset after the final WMMA (LLVM then puts it in a
short-lived low VGPR), and compiling the identical LLVM IR with
`-mattr=-1024-addressable-vgprs`. Both stop the address from depending on the old
`v257`.

**What this corrects in the earlier reading here:** register spilling is *not*
the cause. Measuring `.vgpr_count` on this branch does show the two tiles sitting
in different regimes —

| Tile | LDS | VGPR | Spilled VGPRs | Scratch |
|---|---|---|---|---|
| `BLOCK_N=128` | 32768 | 944, 986, **1024, 1024** | 0, 0, 29, 33 | 0, 0, 84, 92 |
| `BLOCK_N=64` | 16384 | 649, 654, 758 | 0 | 0 |

— but a `waves_per_eu=2` variant with **2372 bytes** of scratch, more than 5× the
spill traffic, passes 4000 iterations, which rules spill traffic out. High
pressure is what *exposes* the victim; it is not the defect. Likewise the coexec
machine schedule is causal in the reduced case and increases exposure, but is not
the whole story: with coexec disabled the full N=128 form still faulted at step 0
in one run, from the same `v257`.

Validation matrix, from [#3](https://github.com/raikonenfnu/training/issues/3):

| Variant | Result |
|---|---|
| Original N=128, extended VGPRs, seed 4321 | fault at step 0 |
| Identical LLVM IR, `-mattr=-1024-addressable-vgprs` | PASS, 4000 iterations |
| Late lane-offset rematerialisation, clean LLIR replay | PASS, 4000 iterations, twice |
| **N=64 application workaround (row 2)** | **PASS, reduced and full, 4000 iterations** |
| `s_nop 7` after every WMMA | **retracted** — passed once, identical repeat faulted at step 0 |
| NOPs around every `S_SET_VGPR_MSB`, `V_NOP`, `s_wait_alu` drains | fault at step 0 |

Newer LLVM does not resolve it: `85c730242e` adds the gfx1250 pre-RA WMMA
co-execution-window model, and Triton `7ff97e3109` actually pins LLVM
`b010a18d`, which predates it — but rebuilding against post-fix `ce352942` still
faults at step 0. So that patch is relevant and insufficient for this A0.

The recommended fix is a subtarget-gated backend erratum: teach register
allocation not to carry cheap, address-critical work-item-derived values in
extended VGPRs across WMMA regions, rematerialising them after instead.
`-mattr=-1024-addressable-vgprs` is the conservative fallback, at the cost of
heavy spilling. **Native cold-boot B0 validation is still owed**, to separate an
A0 silicon erratum from a backend requirement that applies to later steppings;
[#2](https://github.com/raikonenfnu/training/issues/2) carries the six-cell
handoff matrix.

## Still open

- **[3] `train_loss=nan`.** The one defect with no workaround and no standalone
  reproducer. Unassessed on the working stack: the run above is ~9× too short in
  samples. **Next step is a batch-128 run of ≥3000 steps.**
- **[6] upstream.** The LLVM hazard above, plus native B0 validation. Until it
  lands, row 2 is load-bearing and `TRITON_FULL_AUTOTUNE=1` is unsafe on gfx1250.
- **[1] / [1b] buffer-op hangs.** Avoided by a knob, not fixed, and [1b] shows
  the knob does not cover the class. A matched control is owed.
- **Two unquantified perf costs**, rows 2 and 3: the halved attention-backward
  tile, and the loss of software pipelining across the autotuned kernels on
  HIP + Triton ≥ 3.8.
  Both may be recoverable — row 3 possibly just by re-testing on current main.
- **Gate hygiene**, rows 3 and 4: both trigger on Triton ≥ 3.8, which also
  matches upstream `main`. If the defects they cover are fixed upstream, the
  gates are silently costing throughput.

Every reproducer runs in one of the four repo images, which differ only in the

```bash

docker run --rm -it \
```

- **A hang costs a reboot** plus `sudo modprobe amdgpu` afterwards, since `amdgpu`
  is blacklisted on the kernel cmdline. A memory-access *fault* is recoverable —
  the process dies and the GPU comes back. So leave the hang reproducers for last,
  and run **one test per process under a hard timeout**: `pytest` orders
  `unittest` methods alphabetically, so a sweep that wedges blames the wrong test.
- **To name the faulting kernel, set `AMD_SERIALIZE_KERNEL=3`.** It makes the
  async fault synchronous and prints `kernel: <name>`; without it you get only an
  address, and a queue wedged behind the fault looks exactly like a hang.
  `AMD_LOG_LEVEL=3` filtered to `ShaderName` gives the last dispatch before it.
- **A fault writes a coredump the size of allocated VRAM** (9–36 GB observed).
  `HSA_ENABLE_COREDUMP=0` does *not* suppress it on this runtime, so keep
  `HSA_COREDUMP_PATTERN` pointed out of the working tree.
- **Unit tests** need `import fbgemm_gpu` before `pytest` collects, and
  `pip install hypothesis`. In `hstu_attention_test.py`, `test_attn` is a helper
  that `pytest` mis-collects, so name the class test explicitly.
- **E2e reproducers** need the prepared yambda-5b cache under `DLRM_DATA_PATH` and
  go through [`scripts/run_smoke_shrink_1gpu.sh`](../scripts/run_smoke_shrink_1gpu.sh),
  which defaults `AMDGCN_USE_BUFFER_OPS=0` and forwards `IMG`,
  `NUM_TRAIN_BATCHES`, `PROGRESS_EVERY`, `AMD_SERIALIZE_KERNEL`,
  `TRITON_ALLOW_PIPELINING` and `DEBUG_NAN_HOOKS`. Check `ps -eo pid,cmd | grep train_ranker` first — an
  interrupted run can outlive its shell, and two trainings sharing the GPU
  invalidates the result.

## API changes

These are the **Triton language API** edits in this tree that make the HSTU
kernels compile on current upstream `main` (defect [5]). They are not
workarounds for [1]/[4]/[4c]/[6]: `AMDGCN_USE_BUFFER_OPS=0`,
`clamp_num_stages`, and the separated-RNG dropout path still exist, but those
are runtime gates and the kernels already compiled without them.

### What upstream removed

On `triton-lang/triton` after the block-pointer deletion (every `main` we have
tried, including sglang's `76940ad3` pin), `tl.make_block_ptr` raises:

```
NotImplementedError: Block pointers have been removed in favor of the tensor
descriptor API
```

`tl.advance` went with them. Upstream's replacement is
`triton.tools.tensor_descriptor.TensorDescriptor`, which lowers to NVIDIA
Hopper TMA (`cp.async.bulk.tensor.*`). That path is already in the HSTU
attention host wrapper and is **not** what we turned on: `_should_enable_tma()`
returns `False` on HIP, including gfx1250, because gfx950 reports capability
`(9, 5)` and would otherwise pass the Hopper check.

### What we replaced them with

Masked plain-pointer `tl.load` / `tl.store`. The 2-D block-pointer sites map
one-for-one:

| Before (Triton ≤ 3.8 AMD SDK) | After (this branch; compiles on `main`) |
|---|---|
| `tl.make_block_ptr(base=X, shape=(N, D), strides=(stride_x, 1), offsets=(start_row, 0), block_shape=(BLOCK_N, BLOCK_D), order=(1, 0))` | `rows = start_row + tl.arange(0, BLOCK_N)` and `cols = tl.arange(0, BLOCK_D)` |
| `tl.load(ptr, boundary_check=(0, 1), padding_option="zero")` | `tl.load(X + rows[:, None] * stride_x + cols[None, :], mask=(rows < N)[:, None] & (cols < D)[None, :], other=0.0)` |
| `tl.store(ptr, y, boundary_check=(0, 1))` | `tl.store(Y + rows[:, None] * stride_y + cols[None, :], y, mask=…)` |
| `ptr = tl.advance(ptr, (0, BLOCK_N))` (attention K/V tiles) | rebuild the pointer from the physical sequence offset each tile: `K + offset_kh + (seq_start + load_offs_n)[:, None] * stride_kn + …` — there is no longer a cursor to advance |

`boundary_check` + `padding_option="zero"` is the mask; `other=0.0` is the
padding. Nothing else in the kernels needed a language-level rewrite.

### Files

26 `tl.make_block_ptr` call sites and 8 `tl.advance` call sites, all gone.
`grep make_block_ptr generative_recommenders` is empty on this branch.

- `ops/triton/triton_hstu_attention.py` — fused/cached HSTU attention forward
  and backward (`_hstu_attn_fwd`, `_hstu_attn_bwd`, and the one-block helpers).
  **Do not feed the remapped `pos_offs_*` into pointer arithmetic.** Those
  coordinates are for the causal / contextual / multi-target *mask* only; V is
  indexed at the physical sequence offset. Mixing them is a silent layout bug,
  not a compile error.
- `ops/triton/triton_layer_norm.py` — `_layer_norm_fwd`,
  `_weighted_layer_norm_fwd`, `_weighted_layer_norm_bwd_dx`,
  `_weighted_rms_norm_fwd`, `_weighted_rms_norm_bwd`.
- `ops/triton/triton_hstu_linear.py` — the fused layer-norm × mul × dropout
  kernels that used 2-D block pointers for X/Y/U.

Jagged concat/split, position embeddings, and addmm were already on plain
pointers (or on the unused Hopper descriptor path) and did not need a port.

### Compatibility

The same sources still compile and run on AMD 3.6.0 / 3.7.1 / 3.8.0: masked
`tl.load`/`tl.store` was never removed. So this is a **widening**, not a
version-specific fork.

`scripts/attn_check.py` is the numeric check that the port matches the previous
kernels. All eight deterministic BF16 cases pass forward and backward at the
original `atol=1e-5`, `rtol=0.016` — no tolerance changes — on both
`7ff97e3109` and AMD `3.8.0+git4cff872c`:

```bash
env -u TRITON_ALLOW_PIPELINING \
  AMDGCN_USE_BUFFER_OPS=0 AMD_SERIALIZE_KERNEL=3 \
  PYTHONPATH=/path/to/triton/python:. \
  python scripts/attn_check.py
```

Those cases are **fixed-shape, single-shot** launches, which is why they passed
throughout defect [6] and why placing it took so long: what the trainer adds is a
different jagged layout every step. Run this check if these kernels are touched,
but do not read it as clearing the backward.

One related but **not compile-blocking** language tweak:
`ops/triton/triton_position.py` uses `&` / `|` instead of Python `and` / `or`
on boolean masks. Triton now warns (and will error) on the Python operators
inside `@triton.jit`; the kernels already compiled.

## Historical: defects by Triton version

**Reference only.** None of these versions is the recommended path any more —
[the working stack](#the-working-stack) is upstream `main` @ `7ff97e3109` with
the fix set above. This section is kept because it records what each older
Triton does to this workload, which is what you need if you are handed one of
these images, bisecting a regression, or writing up a defect for the Triton team.

All of these are in the Triton path; none is in the benchmark's math. The table
is **ordered by Triton version, oldest first**, so it answers "what breaks on the
version I am about to run". Only the Triton wheel was ever swapped
(`--no-deps`), holding torch, ROCm and driver constant, so Triton is the only
variable across every row.

A defect that spans versions is listed once, with every version it was tested on
in the version column. The `#` column is only row position and renumbers whenever
the table is re-sorted, so **cite a defect by its bracketed id, not by row
number** — row 6 is defect [4]. Those ids are stable and are referenced from code
comments in `common.py`, `ops/utils.py` and `dlrm_v4/train/utils.py`, so keep
them if you re-cut this table. **Tested** is the UTC calendar day the result in
that row was recorded (the latest confirmatory run, if it was re-run), not an id.

Reproducers are split into two columns by what they cost to run: **e2e** needs
the prepared yambda-5b cache and a training run, while **standalone** covers
everything runnable without a dataset. Both cells are always filled, so a "none"

3.7.1 commit `0263a6a6`.  Holding the source, LLVM, input, two-warp launch, and
all other options fixed gives this matrix:

| coexec attribute | expert mode | result | backward VGPRs |
|---|---|---|---:|
| on | on | memory-aperture fault | 254 |
| off | on | correct | 135 |
| on | off | correct | 254 |

The last two rows separate the scheduler defect from register pressure alone.
With both controls enabled, two warps fault and four warps silently corrupt
results; eight warps is correct because Triton does not request coexec above
four warps.  Disabling coexec fixes the two- and four-warp kernels, including
`FAST_DROPOUT=True` and `COMPUTE_Y=False`.

For an unmodified `3.8.0+git4cff872c`, the immediately available compiler
workaround is:

```bash
AMDGCN_USE_BUFFER_OPS=0 TRITON_HIP_USE_EXPERT_SCHEDULING=0 \
  python scripts/repro_gfx1250_fused_rng.py
```

A narrower compiler workaround is to backport ROCm/triton
[`#11272`](https://github.com/ROCm/triton/pull/11272), then run with
`TRITON_HIP_USE_COEXEC_SCHEDULER=0`.  The backport adds a cache-invalidating
knob so toggling the scheduler cannot reuse an incompatible cached binary.  The
existing separated-RNG application workaround remains preferable when only
this operation needs protection; `num_warps=8` is another verified but
performance-untuned kernel workaround.  The recommended image already contains
the proposed ROCm 7.14 / torch 2.11 gfx1250 nightly stack, so reinstalling those
wheels does not address this compiler-scheduling defect.

**Latest-main retest (2026-09-03): fixed.** Upstream `triton-lang/triton` main
at [`7ff97e3109`](https://github.com/triton-lang/triton/commit/7ff97e310935b4a79794878dbc911f9af25d38d9),
built from source with bundled LLVM `b010a18d`, passes the original two-warp
launch and the four-warp and `FAST_DROPOUT=True` corruption cases with default
settings.  The generated LLIR still carries
`"amdgpu-sched-strategy"="coexec"`, expert scheduling is still enabled, and the
two-warp kernel reports 260 VGPRs.  Therefore the row-7 defect does **not**
persist in that current compiler stack; it was fixed by intervening
Triton/LLVM codegen changes rather than by disabling coexec.  The precise
fixing commit has not been bisected.

## The node

1× MI450 A0 engineering sample, `gfx1250`, PCI `1002:75c1`, SKU `M4500001`, rev
`0x00` — 256 WGPs, ~432 GiB HBM, **`warp_size=32`** (RDNA, not CDNA wave64).
ROCm 7.14, torch `2.11.0+rocm7.14.0a20260625`, Triton 3.6.0 stock. Host Linux
`6.14.0-37-generic`, amdgpu DKMS 7.1.1, Docker 29.6.1.

Two facts drive every change here: **one GPU** (the whole model must fit in one
HBM) and **wave32** (CDNA assumptions in fbgemm are wrong).

`amdgpu` is blacklisted by the kernel cmdline
(`modprobe.blacklist=amdgpu,device_dax,dax_hmem`), so after every boot run
`sudo modprobe amdgpu` — `/dev/kfd` appears ~15 s later.

**Recovery from a hang is a reboot.** The process sticks in uninterruptible `D`
state, `docker kill` returns *"did not receive an exit event"*, MODE2 reset fails
with `error code -62`, and `modprobe -r amdgpu` deadlocks. The wedge is
whole-device and survives container teardown: `rocm-smi` still answers while
holding VRAM with no processes alive, and a bare 1024² bf16 matmul in a fresh
container never returns. Untried: `flr`/`bus` reset and the `umr` wave debugger.

## Getting it to run

**Image** — [`Dockerfile.amdprimus0815`](../Dockerfile.amdprimus0815). Stock
`rocm/primus:v26.3` torch has no gfx1250 code objects, so *any* kernel fails with
`CUDA error: device kernel image is invalid`. `amdprimus/amdprimus:0815` has
gfx1250 torch but no fbgemm/torchrec, so those are built on top (~8 min). ROCm
lives in the wheel at `site-packages/_rocm_sdk_devel`, not `/opt/rocm`, so
`ROCM_HOME`/`HIP_ROOT_DIR` must point there or configure dies with
`BUILD_ROCM_VERSION is not set`. Also needs `libtbb-dev`, `libnuma-dev`,
`libssl-dev`, `ninja-build`.

**Three fbgemm patches** — (1) `Fbgemm.cmake` omits `FbgemmFloat16Convert*.cc` /
`FbgemmBfloat16Convert*.cc`, relying on torch's bundled FBGEMM; (2) host/device
**warp-size disagreement**, host assumed wave64; (3) codegen also hardcodes
wave64. With these, TBE is **bit-exact** against CPU.

**Embedding shrink** — `EMBEDDING_ROW_SCALE`; the reference tables are ~559 GiB
of fp32 weights against one ~432 GiB GPU.

**Dataset** — use the **MLCommons prepared download** (README Option A): 227.41
GB, 19 files, all md5/sha256 verified. Do **not** self-preprocess; the cache build
needs ~190 GB RAM and OOM-killed this 251 GB box.

## Performance

Triton 3.7.1, gin-default depth 3, `MAX_SEQ_LEN=4096`, `EMBEDDING_ROW_SCALE=0.25`,
`BATCH_SIZE=128`, buffer ops off — measured in the finite region, while the loss
was still converging. Step 50 is warmup (1920 ms, carrying compile and autotune).
Steady state is **~322 ms/step, ~395 samples/s, `tflops_real` 35–61, HFU
1.1–1.9%**. HFU tracks `fill` (29–49%) rather than being a fixed number, because
`fill` is the fraction of the dense-equivalent work the jagged batch actually
contains.

**Read `hfu`, not `mfu`.** `num_flops_per_sample` is a *static dense* estimate
(315.7 GFLOP/sample at 3 layers) while jagged attention performs only the `fill`
fraction of it, so `mfu` (3.7–4.2%) describes work that is never executed.
`tflops_real` is the honest count and `hfu` its utilization.

HFU is against **3150 TFLOP/s = 90% of the 3500 TFLOPS dense BF16 matrix peak**
for MI450. Two notes on that denominator. `get_gpu_peak_flops` matched nothing and
silently fell back to **MI350X's 2300 TFLOPS**, because these parts report the
generic name `AMD Radeon Graphics`, so every earlier perf line in this repo's logs
is normalized against the wrong chip; it is now keyed on `gcnArchName`. And the
silicon peak is used deliberately, not the ~75 TFLOP/s (~2% of it) this node can
actually reach today: measured bf16 GEMM is only **1.46× fp32** (67.8 vs 46.5 TF
at N=8192), i.e. the **matrix cores are idle** and everything runs on the vector
path at ~1.1 GHz against a 2.4 GHz max clock. Normalizing against measured
throughput would conflate model efficiency with BLAS immaturity and would
silently change meaning as kernels improve.

## Retracted

`and`/`or` on tensors is **not** a bug, and the `triton_position.py` rewrite was
cosmetic. Triton warns `Logical operators 'and' and 'or' are deprecated for
non-scalar tensors`, but `code_generator.py:visit_BoolOp` (3.6.0) lowers them to
`logical_and`/`logical_or`, which for boolean masks is exactly `&`/`|`. Nothing
goes unmasked. The position test passing afterwards was nondeterminism.

**Register spilling is not what causes defect [6]**, and this document said it
was. The `BLOCK_N=128` tile does reach the 1024-VGPR ceiling and spill while
`BLOCK_N=64` does not, which is why the pin works, but the causal chain runs
through an extended VGPR held live across the WMMA region — a `waves_per_eu=2`
variant with 5× the scratch passes 4000 iterations. See [Root cause of the
attention-backward fault](#root-cause-of-the-attention-backward-fault-6--4d).

Also retracted, upstream: **`s_nop 7` after every WMMA is not a fix** for that
defect. It passed 4000 iterations once and an identical repeat faulted at step 0.
The durable controls are late lane-offset rematerialisation and disabling
1024-addressable VGPRs.

Separately, `hstu_compute::test_compute_output` was an **inherited code bug, not a
GPU bug**: the forward dropped `mul_u_activation_type`, so it applied no
activation while its own backward applied one. A one-line fix takes that parameter
grid from 32 mismatches to 0. Our file is byte-identical to
`mlcommons/training@master`, and the defect is dormant in the benchmark, which
only ever passes `"none"`.

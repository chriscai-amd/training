# Bring-up on MI450 A0 (gfx1250, single GPU)

What it takes to run the yambda-5b HSTU ranker on an **MI450 A0 engineering
sample**, why the stock MI350X path does not work here, and where the run
currently stops.

Companion to [`training_recipe.md`](./training_recipe.md) and
[`perf_opt.md`](./perf_opt.md). Everything below is on branch `chcai/mi450_a0`.

---

## TL;DR

- The whole software stack is working: **fbgemm_gpu builds and runs correctly on
  gfx1250**, TorchRec shards the model onto the one GPU, the 4.76B-event dataset
  streams, and the HSTU Triton kernels compile.
- Two classes of change were needed, both orthogonal to the benchmark's math:
  1. **A new image** ([`Dockerfile.amdprimus0815`](../Dockerfile.amdprimus0815)) —
     the stock `rocm/primus` torch cannot launch any kernel on this node, and
     fbgemm needs three source patches because **gfx1250 is RDNA (wave32), not
     CDNA (wave64)**.
  2. **Shrinkable embedding tables** (`EMBEDDING_ROW_SCALE`) — the reference
     tables are ~559 GiB of FP32 weights and there is only one ~432 GiB GPU.
- **Current blocker: a GPU hang in a Triton op kernel.** It is *not* the
  attention kernels — those pass at the workload's exact shape and across 200
  randomized cases. The hang reproduces from the op unit tests alone, with no
  embeddings, dataset or TBE involved, and its signature (100% GFX activity, 0%
  memory traffic, no memory fault) says a kernel is **spinning**, which on a
  wave32 part points at a wave64 assumption.
- Each hang costs a **node reboot**: the MODE2 reset fails (`error code -62`) and
  `modprobe -r amdgpu` then wedges in uninterruptible `D` state.

## The node

| | |
|---|---|
| GPU | 1× MI450 A0 eng. sample, `gfx1250`, PCI `0001:01:00.0` (`1002:75c1`) |
| Reported name | `AMD Radeon Graphics`, **`warp_size` = 32** |
| HBM | ~432 GiB (single device) |
| Kernel / driver | `6.14.0-37-generic`, `amdgpu` |
| Docker | 29.6.1 |

Two facts drive every change in this doc: **one GPU** (so the whole model must
fit in one HBM) and **wave32** (so CDNA assumptions in fbgemm are wrong).

`amdgpu` is blacklisted at boot here, in both `/etc/modprobe.d/amdgpu.conf` and
the kernel cmdline (`modprobe.blacklist=amdgpu,device_dax,dax_hmem`), so after
every boot the driver has to be loaded by hand:

```bash
sudo modprobe amdgpu     # then /dev/kfd appears
```

There is no load script, no `options amdgpu` line and no systemd unit on this
node, so no board-specific module parameters are being missed.

## Part 1: the container image

`Dockerfile` (stock) targets MI350X/gfx950 on `rocm/primus:v26.3`. That image's
torch wheel has no gfx1250 code objects, so *any* kernel fails:

```
torch::AcceleratorError: CUDA error: device kernel image is invalid
```

`amdprimus/amdprimus:0815` ships torch `2.11.0+rocm7.14` **with** gfx1250
support (a plain matmul works), but no `fbgemm_gpu` and no `torchrec`. So
[`Dockerfile.amdprimus0815`](../Dockerfile.amdprimus0815) keeps that torch and
builds the rest on top. Build time is **~8 min** (628 objects, one arch).

### 1a. Build environment

`amdprimus` does not ship ROCm at `/opt/rocm`; it lives inside the torch wheel
at `site-packages/_rocm_sdk_devel`. Without pointing CMake there, fbgemm's
configure dies with `ValueError: BUILD_ROCM_VERSION is not set`. Hence:

```dockerfile
ENV BUILD_ROCM_VERSION=7.14 \
    PYTORCH_ROCM_ARCH=gfx1250 \
    ROCM_HOME=/opt/venv/lib/python3.12/site-packages/_rocm_sdk_devel \
    HIP_ROOT_DIR=/opt/venv/lib/python3.12/site-packages/_rocm_sdk_devel
```

The image also lacks four dev packages that `rocm/primus` has; `libtbb-dev` is
the one that hard-fails the build (`CMake Error: tbb not found`), and
`libnuma-dev`, `libssl-dev`, `ninja-build` are installed alongside it.

### 1b. fbgemm patch 1 — missing fp16/bf16 convert sources

At the pinned FBGEMM commit, `fbgemm_gpu/cmake/Fbgemm.cmake` omits
`FbgemmFloat16Convert*.cc` / `FbgemmBfloat16Convert*.cc` and relies on
**PyTorch's bundled FBGEMM** to provide those symbols. `rocm/primus` torch is
built `-DUSE_FBGEMM` and exports them; amdprimus torch 2.11 does not, so:

```
OSError: fbgemm_gpu/fbgemm.so: undefined symbol:
  _ZN6fbgemm19Float16ToFloat_avx2EPKtPfm
```

Fix: add the six convert sources to the CPU target. This is exactly the source
list upstream HEAD ships, so it is a forward-port, not a workaround.

### 1c. fbgemm patch 2 — host/device warp-size disagreement (wave32)

With fbgemm loading, the TBE **forward** ran but the **backward** died:

```
[backward_cta_per_row_kernel]: [block dim 64 x 32 x 1]
Threads per block 2048 is greater than the limit of 1024
```

`cuda_prelude.cuh` sets the *host-side* `kWarpSize` to 64 for ROCm — its own
comment calls this a "stop-gap" and says host launches should use
`at::cuda::warp_size()`. Device compilation correctly gets 32 (`__GFX9__` is
undefined for gfx12). The backward launch mixes both:

| block dim | value on this GPU | source |
|---|---|---|
| x | `kThreadGroupSize` = `kWarpSize` = **64** | compile-time, CDNA assumption |
| y | `kMaxThreads / at::cuda::warp_size()` = 1024/32 = **32** | runtime, correct |

64 × 32 = 2048 > the 1024 threads/block limit. Upstream HEAD does **not** fix
this for our case: it only drops to a 32-wide group when `max_D <= 128`, and the
workload's table dim is 512.

Fix: pin the host constexpr to 32 so host and device agree. We compile for a
single arch, so a compile-time 32 is correct here.

### 1d. fbgemm patch 3 — codegen also hardcodes wave64

Patch 2 alone produces a *new* load failure, because the kernel instantiations
are emitted by the code generator, which derives the thread-group size from
`items_per_warp // 4` and hardcodes `items_per_warp = 256` (→ 64) for ROCm. The
generated instantiations then no longer match the patched call sites:

```
OSError: fbgemm_gpu_tbe_index_select.so: undefined symbol:
  _Z46batch_index_select_dim0_codegen_forward_kernel...Lm32E...
```

Fix: `items_per_warp = 128` (→ 32) in `codegen/genscript/jinja_environment.py`.

**Patches 1c and 1d must go together.** Either one alone leaves the build
inconsistent.

### 1e. Python deps

`tensordict` is installed `--no-deps` (so pip cannot drag in a CUDA torch),
which also skips its three non-torch runtime imports: `pyvers`, `cloudpickle`,
`orjson`. They are installed in a later layer so they don't invalidate the
fbgemm build.

### 1f. Verification: TBE is bit-exact

Launching without an error is not enough — the wave32 patches change thread
block shapes, so group reductions had to be checked numerically. With
`num_embeddings=1000, dim=512` (the workload's dim) and `EXACT_SGD, lr=1`:

```
warp_size 32
forward   max_abs_err = 0.000e+00
backward  max_abs_err = 0.000e+00
untouched rows drift  = 0.000e+00
RESULT: PASS
```

Bit-exact against `F.embedding` forward and against `w0 - grad` for the fused
optimizer update. FBGEMM does log `Running on non-CDNA architecture.
Performance may be suboptimal.` — correct here, but a perf caveat.

## Part 2: fitting the model in one HBM

The reference yambda-5b tables are 293M rows at dim 512 — 15.1M base id rows plus
278M cross-feature rows, i.e. **~559 GiB** of FP32 weights against ~432 GiB of
HBM on a single device. `EMBEDDING_ROW_SCALE` scales **every** table's row count
by one factor; unset or `1.0` reproduces the reference exactly.

The scale is applied in one place and every consumer derives from it, so the
caps cannot drift apart:

| File | Change |
|---|---|
| `dlrm_v4/configs.py` | `scale_embedding_rows()`, `yambda_5b_cross_specs()`, `yambda_5b_table_rows()`; table configs read row counts from `yambda_5b_table_rows()` |
| `dlrm_v4/datasets/yambda.py` | modulo-wrap `uid`/`item`/`artist`/`album` ids (and the candidate targets) into the scaled vocabulary |
| `dlrm_v4/utils.py` | dataset factory passes `yambda_5b_cross_specs()` |
| `dlrm_v4/train/utils.py` | embedding diagnostics use the scaled cross caps |

Cross features already hash into `num_embeddings`, so they need no wrapping —
only the base id features do, hence the modulo in the dataset.

At `EMBEDDING_ROW_SCALE=0.25`:

```
[embedding-scale] EMBEDDING_ROW_SCALE=0.25 -> item_id=2347656, artist_id=323348,
                  album_id=841923, uid=250000, cross_rows=69500000
```

i.e. ~140 GiB of weights. TorchRec plans the run at **340.0 GB HBM, 85%** of the
400 GB `HBM_CAP_GB` budget (weights plus optimizer state and activations), with
all 11 tables `table_wise` / `compute_kernel=fused`.

> Row scaling changes the model's capacity, so accuracy is **not** comparable to
> a reference run. It exists to prove the pipeline runs end to end on one GPU.

## Part 3: running it

[`scripts/run_smoke_shrink_1gpu.sh`](../scripts/run_smoke_shrink_1gpu.sh) wraps
the whole thing (device flags, data mount, smoke caps):

```bash
docker build -f Dockerfile.amdprimus0815 -t recommendation-amdprimus0815:gfx1250 .
EMBEDDING_ROW_SCALE=0.25 HBM_CAP_GB=400 bash scripts/run_smoke_shrink_1gpu.sh
```

Defaults are smoke-sized, not performance-sized: `BATCH_SIZE=8`,
`NUM_TRAIN_BATCHES=5`, `NUM_EVAL_BATCHES=2`, `NUM_TRAIN_TS=1`,
`HISTORY_LENGTH=4086` (must match the prepared `hstu_cache_L4086/`).

### Dataset

Option A layout under `$DLRM_DATA_PATH` (227 GB), all present and `_READY`:

```
processed_5b/hstu_cache_L4086/   16 files (flat_*, anchor_ts_L4086, positions_L4086, user_*, unique_uids)
processed_5b/item_popularity.npy
shared_metadata/{album,artist}_item_mapping.parquet
```

`FlatEventStore mmap ... 4,763,272,693 events, 1,000,000 users`. The first run
also builds a `positions_L4086_m64.npy` index for `MIN_HISTORY=64` (a few
minutes, cached afterwards).

## Current blocker: GPU hang in a Triton op kernel

How far the full run gets — all of this succeeds:

1. Tables scaled and TorchRec plan produced (340 GB HBM, 11 tables placed).
2. TBE constructed on device (`SplitTableBatchedEmbeddingBagsCodegen`,
   `exact_row_wise_adagrad`, total hash size 73,262,927).
3. Dataset mmapped, positions index built, dataloader workers feeding batches.
4. HSTU Triton kernels (`triton_position.py`, `triton_hstu_attention.py`)
   compile and start executing.

Then, during the first training iterations:

```
HW Exception by GPU node-2 (Agent handle: 0x40660120) reason :GPU Hang
HW Exception by GPU node-2 (Agent handle: 0x2c0bf390) reason :GPU Hang
```

### It is not the attention kernels

The obvious suspect was Triton HSTU attention, since that was the last thing
executing. It has been ruled out:

- A shape walk up to the workload's exact config (`B=8 N=4096 H=4 D=128`, bf16,
  forward **and** backward) passes at every stage, with max error vs the PyTorch
  kernel of `2.4e-04` forward / `7.3e-04` backward — bf16 rounding, nothing more.
- The repo's own `hstu_attention_test.py::test_attn_triton` passes all 200
  randomized cases (ragged lengths, `max_targets` 20/512, `attn_dim` 16–128,
  `contextual_seq_len` 0/10, bf16 and fp32) in 150 s with no hang.

### It reproduces without any of the workload

Running the remaining Triton op tests (`hstu_compute`, `position`, `layer_norm`,
`jagged_tensors`, `mm`) hangs the GPU the same way — with **no embeddings, no
dataset, no TBE and no 340 GB residency**. The repro is therefore a single unit
test, not a six-minute pipeline.

It wedged on the 9th test, right after `layer_norm_test` finished; by declaration
order that is `jagged_tensors_test.py::test_split_2D_jagged_triton`, but pytest
buffers names until a file completes, so **the exact test is not yet confirmed** —
attributing it is next step 1 below.

### The signature points at wave32, not at memory

While hung, for ~14 minutes:

| Signal | Value | Reading |
|---|---|---|
| `GFX_ACTIVITY` | 100 % | a kernel is running, not stalled on a fault |
| `UMC_ACTIVITY` | 0 % | it is doing no memory traffic at all |
| dmesg | no `Memory access fault` | not an illegal address |

A kernel burning the shader engine while touching no memory is a **spin**, i.e. a
loop that never terminates. gfx1250 is wave32 and this code was developed on
wave64 CDNA, so the likely mechanism is a loop or cross-lane reduction whose trip
count or exit condition depends on wavefront width — the same class of assumption
that had to be patched in three places in fbgemm (§1c, §1d).

### Recovery costs a reboot, every time

The MODE2 reset fails identically on every hang:

```
amdgpu 0001:01:00.0: MES(7, 1) failed to respond to msg=REMOVE_QUEUE
amdgpu 0001:01:00.0: MODE2 reset
amdgpu 0001:01:00.0: failed to send mode2 reset, error code -62
amdgpu 0001:01:00.0: Mode2 reset failed!
amdgpu 0001:01:00.0: ASIC reset failed with error, -62
```

After that the GPU stops enumerating (`torch.cuda.device_count()` → 0) even
though `/dev/kfd` and `/dev/dri/*` still exist. Reloading the driver does **not**
help: because the ASIC never resets, `modprobe -r amdgpu` wedges in
uninterruptible `D` state and cannot be killed:

```
[<0>] drain_workqueue+0x99/0x140
[<0>] amdgpu_device_fini_hw+0x495/0x600 [amdgpu]
[<0>] amdgpu_pci_remove+0x51/0x90 [amdgpu]
```

So **a node reboot is the only recovery**, and every experiment costs one. Give
every run a hard timeout and write evidence to disk as it goes — anything held in
a buffer is lost when the GPU wedges.

### Separately: four op tests fail numerically

The same sweep produced 4 failures among its first 8 tests — 2 in
`hstu_compute_test`, 1 in `position_test`, 1 in `layer_norm_test` — which are
wrong results rather than hangs, and so a distinct correctness concern from the
spin above. The details were lost with the buffered output; they need re-running
per test. `rms_norm_test.py` cannot run here at all: it imports Meta's internal
`hammer` module, which is not in this repo.

### Next steps

1. **Attribute the hang.** Run each op test in its own container with a hard
   timeout so one wedge cannot hide the rest, with `-v` for live names and
   `TRITON_PRINT_AUTOTUNING=1` tee'd to disk to capture the config in flight.
2. **Test the wave32 hypothesis** on the identified kernel by restricting its
   autotune space — `num_warps` 8/16 are the usual wave32 casualties, since
   occupancy and LDS budget differ from wave64. If pinning `num_warps=4` clears
   it, that localises the bug to a specific config rather than the kernel.
3. **Get an e2e result in parallel** with `HSTU_HAMMER_KERNEL=PYTORCH`. The
   PyTorch path is the reference in every test that passed, so it is the most
   likely route to a completed smoke run while the Triton spin is investigated.
4. Re-run the 4 numeric failures individually and triage them separately.
5. If the PyTorch path also hangs, bisect the workload down
   (`EMBEDDING_ROW_SCALE=0.05`, `MAX_SEQ_LEN=512`, `HSTU_NUM_LAYERS=1`) to find a
   surviving configuration, then grow back.

> When re-running the op tests standalone, preload fbgemm first — the test
> modules use `torch.ops.fbgemm.jagged_to_padded_dense` but never import
> `fbgemm_gpu` (the training entry point gets it transitively via torchrec):
> `python -c "import fbgemm_gpu, fbgemm_gpu.sparse_ops, pytest, sys; sys.exit(pytest.main([...]))"`.
